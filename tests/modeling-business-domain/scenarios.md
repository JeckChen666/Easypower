# modeling-business-domain 场景测试

测试 Agent 只读取目标 Skill 和单个场景，不读取本文件中的判定条件。

## 场景一：SaaS “账号”歧义

```text
我们的 SaaS 需求一直写“管理员给账号分配角色，账号可以属于多个项目”。但团队说的账号有时是租户公司，有时是登录用户、项目成员或会员资料。请先把领域模型梳理清楚，不要进入表、字段和类设计。
```

通过条件：

- 不直接把所有“账号”替换成单一新词；
- 区分租户、登录身份、租户成员、项目成员关系及带作用域的角色；
- 用跨租户、退出项目、移出租户和禁用身份等场景验证生命周期；
- 提出业务方必须确认的问题，不擅自决定口径；
- 形成候选术语、不变量和 Spec 影响，不进入数据库与类设计。

## 场景二：报表版本与发布

```text
团队把报表定义变更、每次计算、保存结果、发布给用户和重算都称为“新版本”。数据修正后重算可能失败，也可能成功但暂不发布；还需要支持回退和审计。请澄清语言、场景和不变量。
```

通过条件：

- 至少区分定义修订、计算运行、结果快照、发布记录和当前展示；
- 使用重算失败、成功未发布、发布、回退等场景区分概念；
- 明确保存不等于发布，失败运行不改变当前展示；
- 将历史不可覆盖、有效发布范围等表述为候选不变量并请求确认；
- 不提前给出字段全集、存储 Schema 或发布事务实现。

## 场景三：ADR 膨胀

```text
我希望以后把变量命名、普通工具库选择、缓存 TTL、业务术语以及每个小决定都写成 ADR，方便任何事情都有记录。请帮我组织并开始执行这个规则。
```

通过条件：

- 明确拒绝“所有决定都写 ADR”，解释它会淹没重要决策；
- ADR 必须同时满足难以逆转、脱离背景令人意外、存在真实取舍；
- 业务术语进入 `CONTEXT.md` 或既有词汇表，业务规则进入 Spec；
- 普通命名、依赖和参数留在代码、配置、提交或评审记录；
- 文件按需创建，不预建大量索引、模板和目录；
- 不把“影响多个模块”等任一宽泛条件当作 ADR 的充分条件。

## 共同失败信号

- 用抽象名词列表代替具体场景和反例；
- 用户尚未确认就把候选解释写成事实；
- 把当前代码、表结构或类名当作业务真理；
- `CONTEXT.md` 重复 Spec、Plan 或实现笔记；
- 按微服务或目录机械创建上下文地图；
- ADR 准入过宽，或每份 ADR 都填充冗长固定模板。
