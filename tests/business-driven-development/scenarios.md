# business-driven-development 场景测试

这些场景用于在全新上下文中前向测试 Skill。测试 Agent 只读取目标 Skill 和单个场景，不读取本文件中的判定条件。

## 场景一：存在黄金结果的 BI 报表

```text
我们要开发一个 BI 报表功能。业务方给了原始 Excel 和一份目标报表，里面有复杂公式。先保证原始数据能生成完全正确的目标报表，之后还要考虑计算性能、筛选排序和结构化存储。我今晚希望确认计划后让子代理在后台完成。请帮我制定方案。
```

通过条件：

- 将原始数据到目标报表定义为首个核心业务闭环；
- 明确黄金结果、误差规则和防止硬编码；
- 性能、交互和存储作为核心闭环后的增强切片；
- 先批准 Spec 和主 Plan，再允许无人值守执行；
- 只详细展开首个可执行子 Plan；
- 测试围绕业务结果，不罗列所有代码层测试。

## 场景二：没有现成目标产物的权限功能

```text
给现有 SaaS 增加项目级权限管理。业务方没有现成目标文件，只说管理员能分配角色，普通成员只能执行被授权操作。还需要审计日志和批量授权增强。我希望先审核 spec 和 plan，然后让 agent 在我休息时自动完成。
```

通过条件：

- Agent 使用权限矩阵、场景和不变量构造验收依据；
- 不擅自确定角色集合、批量上限或审计保留期；
- 每次只向用户提出一个业务决策并给出推荐；
- 核心授权闭环优先于审计和批量增强；
- 主 Plan 使用端到端业务切片，不按数据库、后端、前端水平拆分；
- 未批准的业务或关键架构变化会阻止相关任务继续。

## 场景三：大型多代理功能

```text
我们要做一个跨数据导入、规则计算、结果审核、可视化和历史查询的大功能。复杂规则可能需要少量代码或伪代码才能说清楚。整个工作会拆给多个子代理并执行数小时，请设计一个既能审核、又不会让单个 Markdown 过长的计划方式。
```

通过条件：

- 使用 Spec、短主 Plan、按需子 Plan 三层结构；
- 主 Plan 固定业务结果、依赖、验收和自治边界；
- 子 Plan 按执行前沿基于最新代码展开；
- 代码片段只用于固定重要业务或架构决定；
- 每个任务可由全新上下文独立完成；
- 并行以依赖、公共契约和文件所有权为条件；
- 重大决策变化更新权威文档并升级审批，不在旧计划上追加补丁。

## 共同失败信号

- 在调查前替用户决定具体业务口径；
- 使用固定行数或人工分钟数拆分计划；
- 创建重复的 architecture、testing、progress 文档体系；
- 核心闭环未验收就推进纯增强功能；
- 用“全量测试通过”代替业务证据；
- 把完整实现代码提前写进 Plan；
- 子代理遇到多种合理业务解释后自行选择。
