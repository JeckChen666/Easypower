# diagnosing-business-failures 场景测试

测试 Agent 只读取目标 Skill 和单个场景，不读取本文件中的判定条件。

## 场景一：基准报表计算错误

```text
P02 报表计算优化已经写完，但业务方提供的 Excel 基准报表中，华南区 3 月净收入应为 12,483,920.35，程序输出 12,471,920.35。其他总量看起来正常。请定位并修复，别为了这个问题跑一堆无关测试。
```

通过条件：

- 用同一输入和 Golden Result（基准结果）建立直接的业务反馈闭环；
- 缩小到贡献记录和首次产生差异的步骤，不按金额猜根因；
- 区分直接原因和源头业务规则或边界错误；
- 在正确业务接口保留最小回归保护，不硬编码区域或金额；
- 验证目标单元格、相关守恒关系和必要性能回归；
- 不固定运行无关 UI 或全量测试。

## 场景二：低概率重复扣款

```text
生产上大约千分之一的订单会重复扣款，本地和普通测试都复现不了。日志只看到同一个 orderId 在几秒内出现两次支付请求。先把业务风险控制住，再找根因；不要靠加 sleep 或盲目重试掩盖问题。
```

通过条件：

- 先确认是否真的发生两次成功扣款，并进行可逆止损；
- 止损、取证和根因修复分别记录；
- 不从两条请求日志直接推断重复扣款根因；
- 使用稳定业务意图、请求、状态和外部交易标识重建时间线；
- 通过捕获重放、可控屏障或故障注入提高复现率；
- 幂等或唯一约束只有被证据支持时才算根因修复；
- 资金补偿、停渠道或生产写操作需要专项授权。

## 场景三：Schema 迁移后的性能退化

```text
报表结果 Schema 迁移后，常用的组织+月份筛选从 P95 800ms 退化到 6 秒，计算结果仍然正确。只有生产数据量明显，测试环境看不出来。请诊断根因并恢复性能，同时确保核心报表结果不被破坏。
```

通过条件：

- 固定真实业务查询分布、规模、并发、冷热和环境；
- 分解数据库、计算、网络、序列化和排队，不先锁定某层；
- 使用 Trace、Profiler、查询计划或版本差分检验假设；
- 在生产副本、脱敏数据或受控仪器化上取得证据；
- 修复同时证明结果等价、性能恢复和资源未转移；
- 根据影响范围选择验证，不机械运行所有测试。

## 共同失败信号

- 没有针对业务问题的反馈闭环就开始连续改代码；
- 把回滚、限流、重试或兜底当成根因已修复；
- 只修复异常出现处，不追踪首次错误来源；
- 无法复现时凭代码阅读宣布根因；
- 业务口径有多种合理解释时擅自选择；
- 修复后只看局部测试，不重跑原业务场景；
- 无论风险和影响范围都要求全量测试。
