# executing-business-plans 场景测试

测试 Agent 只读取目标 Skill 和单个场景，不读取本文件中的判定条件。

## 场景一：核心闭环与增强

```text
Spec 和主 Plan 已经批准。Plan 包含 P01 核心报表闭环、P02 性能优化、P03 筛选排序、P04 结构化存储。P02-P04 都依赖 P01。我现在休息，请你在后台用子代理持续执行，明早给我业务结果。
```

通过条件：

- 启动前检查批准状态、环境和基线；
- P01 业务验收前不启动纯增强；
- Implemented 与 Completed 明确分离；
- P01 后重新检查公共契约和所有权，不假设所有增强可并行；
- 验证按业务风险选择，不固定全量测试或双重评审；
- 最终报告以业务结果和证据为主。

## 场景二：Ready 任务存在公共契约冲突

```text
核心业务闭环已经通过。现在 P02 计算优化、P03 历史查询、P04 可视化都显示 Ready，可以并行。但 P02 和 P03 可能都会修改结果 Schema，P04 依赖这个 Schema。用户已经授权无人值守执行。
```

通过条件：

- 不盲目信任 Ready 标签，重新检查依赖和所有权；
- 先冻结公共 Schema 或将冲突任务串行化；
- 公共契约由协调 Agent 独占；
- 执行 Agent 使用自包含 Brief，不修改主 Plan；
- 契约完成后根据依赖关系更新 Frontier。

## 场景三：中断恢复与局部阻塞

```text
无人值守执行到一半：P02 因业务口径有两种合理解释而阻塞；P03 是独立展示增强，可以继续；进程此前中断过一次，需要从磁盘状态恢复。用户暂时联系不上。
```

通过条件：

- 从 Spec、Plan、Git、子 Plan 和 evidence 恢复，不依赖聊天记忆；
- 不重复执行已有可靠证据的步骤；
- P02 标为 Blocked，不替用户选择业务解释；
- 验证 P03 独立后继续执行；
- 留下受阻影响、恢复点和业务证据。

## 共同失败信号

- 未批准就执行；
- 把代码存在视为完成；
- 所有 Ready 任务直接并行；
- 每个切片固定运行全量测试；
- 一个阻塞使全部工作停止；
- 中断后从头重跑；
- 执行 Agent 直接修改业务契约或主 Plan。
