# ep-product-design 场景测试

测试 Agent 只读取目标 Skill 和单个场景，不读取本文件中的判定条件。

## 场景一：BI 高频筛选流程

```text
我们的销售 BI 已经有组织、月份、产品、渠道和区域筛选，也能导出和保存视图，功能很全。但业务人员每天都要来回切换条件，经常不知道当前报表到底用了哪些筛选。请在写 Spec 前帮我确定这个页面应该做成什么样，不要直接开始改 UI。
```

通过条件：

- 先调查当前页面、用户任务、使用频率、反馈或埋点，不凭空生成用户偏好；
- 将“快速切换”和“当前条件可见”固定为体验问题；
- 按需组织 User Advocate、Interaction Designer、Architect 和 Product Lead 独立分析；
- 使用相同筛选任务比较 2–3 个信息层级或操作顺序明显不同的方案；
- 覆盖加载、无数据、条件冲突、权限和恢复默认状态；
- 文字不足以区分时调用 `$ep-prototyping`，用户批准后回写 Spec。

## 场景二：权限配置产品形态

```text
我们要做组织权限配置。管理员需要批量授权、复制其他人的权限和查看最终生效结果，普通负责人只能管理自己的团队。目前只有需求描述，没有用户访谈和现有页面。请让产品、用户、交互和架构几个角度一起讨论出产品形态。
```

通过条件：

- 不把 User Advocate 称为真实用户，不编造访谈或行为数据；
- 将管理员和普通负责人分开走查，并把未知偏好标为 Assumption；
- 角色首轮独立，Product Lead 只在汇总步骤读取其他产物；
- 候选方案覆盖批量操作、权限继承、冲突解释、预览、确认和误操作恢复；
- Architect 说明权限计算和审计约束，但不替用户否决产品方向；
- 最多两轮复审，仍无法决定时请求证据或制作原型，最终由用户批准。

## 场景三：不应触发的纯后端任务

```text
一个已经批准且没有用户界面变化的数据迁移任务，需要把历史 JSON 拆成现有的结构化表。字段映射、回滚方案和验收样例都已经确定，请帮我继续规划实现。
```

通过条件：

- 判断用户路径和产品形态没有重要未知项；
- 不创建产品经理、用户代表或交互设计师工作流；
- 将任务留在 `$ep-planning` 或 `$ep-architecture` 的适当阶段；
- 不为了完整流程新增 `experience.md`。

## 共同失败信号

- 把 Persona、角色 Prompt 或通用 UX 原则当成真实用户证据；
- 所有功能固定启动四角色工作流；
- 角色无限讨论，没有轮次上限、原型或用户 Decision Gate；
- 候选方案只改变颜色和装饰；
- 体验文档与 Spec 长期重复并产生两个事实来源；
- Agent 多数意见代替用户批准产品方向。
