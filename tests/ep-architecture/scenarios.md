# ep-architecture 场景测试

测试 Agent 只读取目标 Skill 和单个场景，不读取本文件中的判定条件。

## 场景一：BI 计算与交互负载

```text
现有 BI 报表服务用 Python 读取业务方 Excel，计算后把整份结果塞进 JSON，由 Node API 返回给页面。现在数据会从 500 万行增长到 1 亿行，用户还希望按组织、时间和产品交互筛选排序。Excel 目标报表仍是业务正确性的依据。请帮我设计下一版架构，不要只给一个死的性能指标。
```

通过条件：

- 先区分标准生成、交互查询、导出或重放等业务负载；
- Excel 作为业务正确性证据，而不是继续充当线上计算架构；
- 至少比较最小演进和分析服务层等两个可行方案；
- 同时考虑计算、存储、查询、权限、版本、迁移和运维；
- 具体产品选择受真实查询与组织约束约束；
- 性能验证包含结果等价和多维负载，不使用单一死指标。

## 场景二：订单定价模块

```text
订单定价规则散落在 controller、数据库查询、前端和三个工具类里，每次促销变化都要改很多地方。它还依赖库存、会员和第三方税务服务。我们想重构，但不想为了测试制造很多抽象层。请设计业务架构和接口。
```

通过条件：

- 先确认定价不变量、变化热点和外部依赖的业务语义；
- 比较至少两个接口或模块边界，而非直接输出大量完整代码；
- 推荐小接口、深实现，让业务规则变化集中；
- 只在真实替代、远程失败或协议变化处建立 Adapter；
- 测试通过业务接口验证定价结果，不暴露测试专用接缝；
- 业务规则与关键接口决定逐项请求用户批准。

## 场景三：大 JSON 的渐进存储演进

```text
报表结果现在以大 JSON 文件保存。业务希望支持历史查询、版本追溯和重新计算，但不能一次停机迁移，也不确定应该用关系库、列式库还是对象存储。请比较方案并给出可渐进落地的架构决定。
```

通过条件：

- 先区分历史定位下载、字段级查询、跨版本分析和重算；
- 比较单一存储与控制面/产物/可重建查询层等方案；
- 说明事实源、版本、血缘、一致性和失败语义；
- 推荐取决于实际读写负载、团队能力和运维成本；
- 迁移包含双写或影子读、差异验证、灰度和回滚；
- 不因技术偏好提前锁定关系库、列式库或对象存储产品。

## 共同失败信号

- 未调查业务负载和现有约束就指定技术产品；
- 只给一个方案或用虚假陪衬制造选择；
- 只分析计算性能，忽略存储、查询、迁移和恢复；
- 用单一峰值或响应时间作为完整架构依据；
- 为测试创建大量一层转发接口；
- 把架构讨论扩写成生产实现或重复 Spec/Plan；
- 未经用户批准就回写关键架构契约。
