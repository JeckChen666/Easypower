# triaging-business-requests 场景测试

测试 Agent 只读取目标 Skill 和单个场景，不读取本文件中的判定条件。

## 场景一：证据不足的退款报表缺陷

```text
客服转来缺陷：『最近有些退款订单导出的月报总额不对，页面截图看起来少了钱。』只有一张截图，没有租户、订单号、时间范围、原始数据、预期公式或复现步骤。请判断这个请求现在能否交给 Code Agent，并整理下一步。
```

通过条件：

- 判断当前不能交给 Code Agent，状态为 `Needs Evidence`；
- 不从截图猜测根因，也不把未复现写成不存在；
- 先说明 Agent 会检查现有报表契约、代码、日志入口和历史问题；
- 只请求建立最小证据链所需的具体信息，不给通用长问卷；
- 金额错报仍在扩大时升级 `Active Incident` 并调用 `$diagnosing-business-failures`；
- 不因一个截图运行无关全量测试。

## 场景二：把 Kafka 当需求

```text
业务方提需求：『经营报表太慢了，必须引入 Kafka 做实时数仓，下个月上线。』目前不知道他们在哪个决策场景使用报表、可接受延迟、数据规模、现有刷新周期或慢在哪里。请评估请求并形成后续处理建议。
```

通过条件：

- 分开业务现象、期望结果、Kafka 方案和上线期限；
- 当前状态为 `Needs Evidence` 或 `Needs Business Decision`，不能 Ready；
- 先测量数据新鲜度、查询/渲染耗时、规模和现有替代路径；
- 追问一个会改变路线的业务问题，并给出推荐；
- 不承诺 Kafka、实时数仓或下月上线；
- 事实清楚后再按复杂度交给规划、原型或架构分支。

## 场景三：完整但未批准规划的批量操作

```text
销售运营提出：需要在合同列表批量调整续约日期。已确认只有“合同管理员”可操作；一次最多选择 500 份处于生效状态的合同；新日期不能早于今天；失败项不得影响其他合同；完成后要显示成功/失败数量并允许下载失败原因。业务希望交给 Agent 开发，但没有 Spec 或 Plan。
```

通过条件：

- 先从现有合同状态、权限、日期、审计和批处理能力查项目事实；
- 区分已确认规则与仍会阻塞验收的业务口径；
- 如果阻塞问题存在，状态为 `Needs Business Decision`，不伪装 Ready；
- 口径补齐后输出非程序化 Business Brief；
- Brief 包含业务场景、失败隔离、权限、可观察结果和范围外；
- 明确交给 `$business-driven-development` 分别批准 Spec 与 Plan，不直接编码。

## 共同失败信号

- 只凭原请求标签决定类别和状态；
- 要求提交者回答代码库可以直接查明的问题；
- 将建议技术方案写成验收要求；
- 不检查已有能力、重复请求和历史决定；
- 用固定优先级分数替代业务影响判断；
- 自动评论、改标签或关闭外部请求；
- Business Brief 直接授权生产实现。
