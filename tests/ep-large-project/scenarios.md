# ep-large-project 场景测试

测试 Agent 只读取目标 Skill 和单个场景，不读取本文件中的判定条件。

## 场景一：ERP 替换计划

```text
我们要在未来半年把十年前的 ERP 替换掉，范围包括商品、采购、库存、订单、财务对账和 BI。现状文档不完整，库存批次和成本口径没人说得清，是否双写、怎么迁历史数据、先切哪个业务也没决定。这个工作肯定超过一次 Agent 会话。请先帮我组织起来，并尽量让多个 Agent 可以持续推进。
```

通过条件：

- 先与用户批准一个“达到什么状态才能写 Spec”的 Destination；
- 广度识别业务口径、现状事实、迁移和切换等决策域，不直接给半年排期；
- 只把现在能精确提问的内容变成 Decision Ticket，其余保留为 Fog；
- 票据围绕决策而非商品/后端/测试等实施分工；
- 研究可后台并行，库存和成本口径等业务决定必须等待用户确认；
- 主地图、单票据和下一会话入口足以跨上下文恢复。

## 场景二：模糊的 BI 平台统一

```text
我们想把散落在 Excel、Python 脚本和旧 BI 中的经营报表统一成一个可维护的平台。现在只知道最终要让业务自助查看可信报表，但指标口径、数据所有权、刷新频率、权限、迁移顺序和平台选型都还模糊。请建立一个可以跨很多会话持续推进的工作地图；未知问题不要现在假装拆成详细实施任务。
```

通过条件：

- Destination 以业务结果和 Spec 就绪为终点，不提前锁定平台；
- 区分精确决策问题、仍无法准确提问的 Fog 和范围外内容；
- 指标口径、所有权等真实依赖决定 Frontier，不用固定阶段替代依赖；
- 平台选型只有驱动因素清楚后才进入 Ready；
- 一次会话只领取一张决策票据，完整结论不复制到主地图；
- 地图完成后显式交给 `$ep-planning`，不直接开始建设平台。

## 场景三：已经清楚的小功能

```text
我们已经有批准的需求：在订单列表增加按客户名称筛选，接口、字段、交互和验收样例都明确，预计改一个后端查询和一个前端筛选框。为了保险，请帮我建立一个跨会话的大型工作地图，把所有可能的决策都拆成票据。
```

通过条件：

- 明确判断不需要 Wayfinding，不创建地图或大量票据；
- 不重新打开已经批准的业务决定；
- 已有 Spec 和 Plan 时交给 `$ep-execution`；
- 只有 Spec 清楚但 Plan 尚未形成时才交给 `$ep-planning`；
- 实现中发现真实新歧义时再建立对应的单项阻塞或决策分支。

## 共同失败信号

- 一开始生成完整项目目录、实施 backlog 和半年路线图；
- 把所有想到的问题都变成票据，消除 Fog；
- 地图正文复制每个票据的调查和讨论；
- 用“进行中”等模糊状态隐藏领取、阻塞和决策责任；
- Agent 自行批准业务范围、口径或重要架构取舍；
- 将 Wayfinding 变成 issue tracker 安装流程或长期项目管理系统。
