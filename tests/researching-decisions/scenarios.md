# researching-decisions 场景测试

测试 Agent 只读取目标 Skill 和单个场景，不读取本文件中的判定条件。

## 场景一：供应商 API 能力

```text
请调查我们准备接入的支付供应商是否支持请求幂等、批量查询和退款重试。我们要把结论写进 Spec，但不能只引用博客或搜索摘要。供应商产品版本和地区可能有差异。
```

通过条件：

- 先固定供应商、产品、版本、地区、账户和环境；
- 坐标不足时不写具体支持结论；
- 优先官方 API、版本资料、第一方支持和 sandbox；
- 逐项调查幂等、批量查询、退款重试的失败语义和限制；
- 文档未提及保持 Unknown，不推断不支持；
- 输出事实、推论、未知和 Spec 影响，并附精确来源。

## 场景二：框架 v4 到 v5 升级

```text
我们准备把当前框架从 v4 升级到 v5。请调查认证中间件、路由行为和 Node 版本支持是否有破坏性变化，结论必须能让架构和 Plan 直接引用，并明确哪些是官方事实、哪些只是我们的推论。
```

通过条件：

- 未给框架名称和精确版本时先澄清，不假设 Express 或其他产品；
- 固定框架、认证包、目标版本、Node 与部署环境；
- 官方迁移指南、release notes、包元数据和项目锁文件分别作为证据；
- 最低兼容版本与生产推荐明确分开；
- 官方事实、项目事实、影响推论和建议使用不同标签；
- 未知项成为 Plan 的调查或阻塞条件，不伪装为无风险。

## 场景三：具体 Excel 算法等价

```text
我们想知道新的并行报表算法在业务方那份 Excel 数据上是否仍能算出完全一样的结果。能不能先查资料研究一下，直接决定是否采用？
```

通过条件：

- 判断资料研究不能证明具体数据运行结果；
- 明确调用 `$prototyping-decisions` 或业务差分验证；
- 使用同一输入运行新旧算法并比较黄金结果；
- 明确精度、舍入、行序、空值、错误值和格式的等价定义；
- 资料只补充算法风险和 Excel 语义，不直接批准采用。

## 共同失败信号

- 缺少对象坐标时自行假设熟悉产品；
- 用博客、搜索摘要或模型记忆支撑关键结论；
- 只给链接，不说明引用支持哪条主张；
- 把文档沉默解释为不支持；
- 混合官方事实、项目影响和推荐；
- 为小问题调度大量重复研究代理；
- 用资料代替具体业务运行验证。
