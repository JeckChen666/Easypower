# 系统化调试

随机修改会隐藏根因并制造新问题。先收集证据、定位故障链，再选择修复方案。

**核心原则：根因未确认前，不得提交修复。**

## 何时使用

任何测试失败、运行时错误、性能退化、构建异常、竞态、状态污染或“偶尔发生”的问题都使用本流程。生产紧急情况可以先恢复服务，但仍须随后完成根因调查。

## 四个阶段

### 阶段一：观察并复现

1. 完整阅读错误消息、堆栈、日志和失败测试。
2. 记录最小复现命令、输入、环境和出现频率。
3. 确认失败稳定可复现；若不稳定，收集更多日志，不要随意增加重试或超时。
4. 运行通过的相邻用例，确定边界。

### 阶段二：追踪数据和控制流

从失败点向上追踪输入、状态、配置和调用者。对每一层询问：

- 这里收到的值是否已经错误？
- 哪一步首次产生了错误值？
- 谁创建、修改或持有这个状态？
- 哪个假设被违反？

不要停在“这里抛错”这一表象；找到最早能解释失败的错误条件。

### 阶段三：提出并证伪假设

一次只保留一个可检验假设，写出支持和反驳它的证据，再运行最小实验。优先检查最近改动、边界值、环境差异、时序和资源生命周期。没有证据时明确标为假设，不要称为根因。

### 阶段四：修复并验证

1. 为已确认的根因写一个能在失败时保护行为的回归测试。
2. 用最小改动修复根因，不要只修复表象。
3. 运行回归测试，随后运行相关测试和完整套件。
4. 若失败仍存在，回到阶段一；不要叠加未经验证的补丁。

## 时序问题

用条件或事件等待替换 `sleep` 和任意超时。等待应包含超时上限，并在超时时输出状态、上下文和最后一次观察值。若并发测试互相污染，使用 `find-polluter.sh` 二分定位产生状态的测试。

## 分层防御

修复输入边界后，再在领域层和副作用边界增加必要的断言或校验。每层应捕获自己能理解的错误并保留上下文，但不要无差别重复同一检查。详细模式见 `defense-in-depth.md`。

## 红旗：立即停止并回到证据

- 还没读完堆栈就开始改代码。
- “先试一下”连续修改多个地方。
- 只增加超时、重试或日志，却没有验证假设。
- 只修改失败断言让测试变绿。
- 根因不清楚却声称已修复。
- 测试失败后继续做无关任务。

## 快速记录模板

```text
现象：
复现：
首次错误位置：
数据/控制流：
已排除的假设：
确认的根因：
回归测试：
修复及验证：
```

需要深入追踪时阅读 `root-cause-tracing.md`；需要可靠等待时阅读 `condition-based-waiting.md`；需要多层校验时阅读 `defense-in-depth.md`。
