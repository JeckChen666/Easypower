# Spec 协议

Spec 是经用户批准、供所有执行 Agent 共同遵守的业务事实来源。它定义“为什么做、做成什么、如何证明”，不展开任务顺序和普通实现。

## 决策责任

| 信息类型 | 处理方式 |
|---|---|
| 仓库、数据或文档中可查的事实 | Agent 调查并附证据，不询问用户 |
| 业务目标、口径、范围和取舍 | Agent 提出推荐，用户决定 |
| 外部事实或必须运行才可判断的问题 | 先 Research 或 Prototype |
| 重要接口、计算、存储或系统架构取舍 | 调用 `designing-business-architecture` |
| 可逆且不影响业务契约的实现细节 | 留给执行 Agent |

Agent 不要只问“验收标准是什么”。先根据业务场景提出具体样例、不变量或可观察结果，让用户确认或修正。

## 可选决策分支

- **Research**：事实依赖官方文档、源代码、规范或外部系统时使用。记录来源和结论。
- **Prototype**：状态、计算或交互必须运行或展示后才能判断时使用。原型只回答一个问题，不追求测试、持久化和工程完整性；保留结论，生产代码重新实现。
- **Architecture**：公共接口、数据模型、计算引擎、存储或迁移架构难以逆转时，调用 `designing-business-architecture`。基于业务负载比较至少两个可行方案，取得用户批准后回写质量属性、关键决定和计划约束。

这些分支只处理会影响 Spec 的重要未知项，不成为每个功能的固定步骤。

## 构造验收依据

按场景选择最少但充分的验收方式：

| 场景 | 首选依据 |
|---|---|
| 数据计算或转换 | 业务样例、黄金结果、公式、误差规则 |
| 用户流程 | 操作后的可观察状态和结果 |
| 状态机 | 允许与禁止的状态转换 |
| 权限 | 角色、资源、动作和允许/拒绝矩阵 |
| 外部集成 | 请求响应契约、幂等与失败行为 |
| 性能 | 工作负载、当前基线、测量方法和目标 |
| UI | 关键用户路径、交互状态和必要视觉证据 |

没有现成目标产物时，组合以下方法：代表性输入输出样例、决策表、业务不变量、契约、变形关系和用户可观察结果。硬性能指标只有在业务规模和测量方式明确时才进入验收契约。

## 增强扫描

核心闭环明确后，从以下角度寻找候选增强，并只写入用户批准纳入本次交付的项目：

- 计算：算法、批处理、并行、增量、缓存和资源使用；
- 展示：筛选、排序、反馈、可访问性和高频操作效率；
- 存储：结构化模型、索引、版本、追溯、迁移和查询方式；
- 运行：安全、恢复、观测、部署和维护成本。

每项增强必须说明业务价值和独立验收方式。没有价值依据的技术优化留在范围外。

## 批准门槛

- 核心业务闭环完整且可执行验收；
- 当前交付的增强项及优先级已确认；
- 关键规则、不变量、误差和失败行为没有歧义；
- 阻塞实施的业务与架构问题已解决；
- 范围外内容清楚；
- 用户明确将状态改为“已批准”。
