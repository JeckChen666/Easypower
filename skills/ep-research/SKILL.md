# 调研决策依据

## 不要进入本 Skill

- 问题可以用官方文档或现有代码直接读懂 → 直接查
- 是具体业务数据/性能/交互是否成立 → 走 `$ep-prototyping` 或业务验证
- 是多方案系统取舍 → 把研究事实交回 `$ep-architecture`
- 对象/版本/地区等关键适用条件未知 → 先停下来询问

## 入口检查

- [ ] 待决问题依赖外部事实（官方能力、版本兼容、协议、法规、SDK 行为）
- [ ] 至少有一个具体的产品/库/规范作为研究对象
- [ ] 有可访问的一手来源（官方文档、源代码、规范）
- [ ] 没有更好的入口（业务验证走 `$ep-prototyping`,系统取舍走 `$ep-architecture`）

## 输出契约

- 调研范围声明（决策问题、对象、版本、地区、停止条件）
- 每条主张附一手来源 ID + URL/路径 + 适用范围
- 事实 / 推论 / 建议 / 未知项 四层分明
- 决策影响：哪些回写 Spec,哪些交给架构,哪些留 Unknown
- 详细协议见 [source-evidence.md](references/source-evidence.md)、[synthesis-protocol.md](references/synthesis-protocol.md)

## 核心原则

Research（资料调研）只为一个待决问题收集足够的一手事实。先明确对象和适用范围，逐条保存可追溯来源，并分开记录官方事实、项目事实、推论、建议和 Unknown（未知项）。搜索摘要、博客和模型记忆只能帮助发现线索，不能作为决策证据。

## 1. 明确调研范围

写明：

```markdown
**决策问题：**
**需要确认的事实：**
**对象/产品：**
**版本/日期：**
**地区/账户/环境：**
**已知项目约束：**
**不研究：**
**停止条件：**
```

缺少会改变答案的适用条件时，先从仓库、锁文件或用户获取。不要用自己熟悉的框架、地区或版本替代未知对象。用户暂时不在时，可以调查不受缺失信息影响的共同事实，但具体结论必须保持为 Unknown。

## 2. 判断是否应研究

适合研究：官方能力、版本兼容、协议、法规、SDK 行为说明、外部限制和现有源代码事实。

如果问题是具体数据、交互或运行行为能否成立，明确调用 `$ep-prototyping` 或建立业务验证；如果是多方案系统取舍，将研究事实返回 `$ep-architecture`。不要用资料推断具体业务数据运行结果。

## 3. 建立来源计划

读取 [source-evidence.md](references/source-evidence.md)。优先级通常是：正式规范/法规与官方 API 参考、版本化官方文档和 Release Notes（发布说明）、第一方源代码/类型/包元数据、第一方支持答复与可复现实验。社区内容只用于找到一手入口。

只有调研范围较大、各项事实来源互不依赖时才并行调查；小问题直接顺序完成。Agent（协调代理）负责统一适用范围、处理冲突和写最终结论，不要把多个代理摘要直接拼成最终判断。

## 4. 逐条记录证据

每条重要主张保存：稳定 ID、原文或精确位置、URL/文件路径、发布者、版本或更新时间、访问日期、适用范围和证据等级。链接到首页不等于支持具体结论。

来源未提及某能力时只能写“未找到官方证据”，不能写“不支持”。无法打开、版本不匹配、地区不同或内容已过期时降低结论强度并保留 Unknown。

## 5. 处理冲突与空白

对冲突来源先检查产品、版本、地区、端点和日期是否不同。版本化官方资料通常优先于通用说明；可运行源代码可以解释当前行为，但不自动等于供应商承诺的公共契约。

官方资料仍有空白时，按成本选择：第一方支持确认、在 Sandbox（隔离测试环境）中做技术可行性验证、检查项目源码，或将问题标为 Blocked。不得用二手文章投票决定事实。

## 6. 汇总决策证据

读取 [synthesis-protocol.md](references/synthesis-protocol.md)。输出顺序：

1. 直接回答及适用范围；
2. 官方事实台账；
3. 项目事实；
4. 基于哪些事实产生的推论；
5. 条件建议及其前提；
6. 未知项、冲突和需要实测的问题；
7. 对 Spec（业务规格）、架构或 Plan（执行计划）的影响。

研究 Agent 可以给出推荐；业务选择由用户批准，系统取舍由架构 Skill 批准。没有足够证据时给出“条件结论”，不要为了结束任务强行二选一。

## 7. 保存与回写

简单研究直接写入上游决策依据并附来源。需要多个来源、会跨上下文复用或可能审计时，保存一份短研究记录到项目现有约定；没有约定时使用 `docs/easypower/<feature>/research/<decision>.md`，不同时创建摘要、笔记和报告三套文档。

用户批准结论后，将业务可见事实回写 Spec，将架构约束交给 `$ep-architecture`，将实现与验证约束回写 Plan。保留访问日期和重新核验触发条件，例如供应商版本、地区或账户能力改变。

需要完整示例时读取 [vendor-api-example.md](references/vendor-api-example.md)。

## 完成条件

- 调研范围和适用条件足以限定答案；
- 每个关键主张有匹配范围的一手来源；
- 事实、推论、建议和未知项清楚分层；
- 冲突来源得到解释或明确保留；
- 结论直接支持待决问题而非泛泛资料汇总；
- 上游知道可以决定什么、仍需实测什么以及何时重查。

## 常见错误

- 对象不明时自行假设成某个熟悉产品。
- 引用搜索摘要、博客或文档首页支持精确主张。
- 把“文档未提及”写成“不支持”。
- 混淆框架最低兼容版本和生产推荐版本。
- 把项目影响推论写成官方声明。
- 为一个小问题调度多个代理并重复搜索。
- 用资料研究替代具体业务数据、性能或交互验证。
