# 对抗性审查（Adversarial Review）

主 Plan 写完后、用户审批前，主 Agent 并行 spawn 多个只读子代理从不同视角审查 Spec 和主 Plan。本文件提供标准视角 Prompt 模板和整合协议。

## 触发条件

满足以下**任一**条件时默认触发：

- 任务规模属于重度（跨切片、跨上下文、复杂业务闭环）
- Spec / Plan 涉及公共接口、跨模块依赖或不可逆决定
- 用户明确要求"对抗性审查""多视角评审"

不触发的情况：

- 轻量或中等规模任务
- 重构任务（重构有自己的目的探测 + 修改幅度审查，见 `ep-planning/SKILL.md`）
- 已有明确 Spec 和 Plan，用户只需批准

## 子代理视角

按问题特征选 2-3 个视角，**不要全部跑**。每个视角独立 spawn 一个子代理。

### 视角 1：产品经理（PM）

**职责：** 从用户价值和业务范围角度审查

**Prompt 模板：**

```markdown
你是产品经理视角的审查者。只读权限,不要修改任何文件。

请审查以下 Spec 和主 Plan,从用户价值、业务范围、可验收性三个维度给出意见:

- 用户路径是否成立?用户能顺畅完成关键任务吗?
- 范围是否有遗漏(用户没说但实际需要)或越界(超出实际需要)?
- 验收标准是否对用户可观察?还是只描述了内部行为?
- 是否有"以后可能用到"的范围蔓延?是否违反第一性原理(只解决已确认场景)?
- 业务规则是否清晰到可执行?是否存在多种解释?

Spec: <路径>
主 Plan: <路径>

返回结构:
- 发现的问题(按严重度排序)
- 推荐的修改方向
- 仍需要用户确认的开放问题
```

**职责：** 从系统结构和技术合理性审查

**Prompt 模板：**

```markdown

请审查以下 Spec 和主 Plan,从公共接口、计算、存储、迁移、可逆性五个维度给出意见:

- 公共接口是否最小?是否泄露了不必要的复杂度?
- 数据模型是否过度设计?是否存在为未来场景预留的字段/Schema?
- 切片划分是否合理?是否存在应该合并或拆分的切片?
- 迁移、回滚、双跑路径是否实际可执行?
- 是否存在更简单的替代方案?是否符合"现在简单、以后再升级"?

Spec: <路径>
主 Plan: <路径>

返回结构:
- 发现的问题(按严重度排序)
- 推荐的修改方向
- 仍需要用户确认的开放问题
```

### 视角 3：用户代表（User Advocate）

**职责：** 从高频任务和体验摩擦点审查

**Prompt 模板：**

```markdown
你是用户代表视角的审查者。只读权限,不要修改任何文件。

注意:你不能凭空代表真实用户,只能基于 Spec 中已记录的用户证据或场景做出判断。

请审查以下 Spec 和主 Plan,从高频任务、摩擦点、信息层级、状态可理解性四个维度给出意见:

- 高频任务是否能用最短路径完成?是否存在多余步骤?
- 信息层级是否清晰?关键信息是否突出?
- 状态(空/加载/错误/权限)是否对用户可理解?
- 边界场景的体验假设是否合理?是否需要标注为待验证?

Spec: <路径>
主 Plan: <路径>

返回结构:
- 发现的问题(按严重度排序)
- 推荐的修改方向
- 待验证的体验假设清单
```

### 视角 4：QA / 验证

**职责：** 从业务规则可验证性和证据链审查

**Prompt 模板：**

```markdown
你是 QA / 验证视角的审查者。只读权限,不要修改任何文件。

请审查以下 Spec 和主 Plan,从业务规则可观察性、不变量可验证性、证据链完整性三个维度给出意见:

- 每条业务规则是否有可观察的验收方式?
- 业务不变量是否能在最高层业务接口验证,而不是只依赖单元测试?
- 证据是否引用了正确的输入、版本、口径?
- 核心业务闭环是否有清晰的回归方案?
- 是否存在难以验证或只能间接验证的规则?

返回结构:
- 发现的问题(按严重度排序)
- 推荐的修改方向
- 难以验证的规则清单
```

## 整合协议

主 Agent 收集所有子代理评论后,按以下步骤整合:

1. **去重:** 多个视角提到同一个问题合并为一条
2. **分类:** 按 Blocker(必须修)/ Important(交付前修)/ Minor(建议修)/ Question(需澄清)分档
3. **判断采纳:** 主 Agent 主动决定哪些修改、哪些忽略,不机械照搬
4. **修改 Spec / Plan:** 主 Agent 是唯一写权限,直接在原文件修改
5. **写审查记录:** 在 `docs/easypower/<feature>/review.md` 留下简短摘要:

```markdown
## 对抗性审查记录

**执行时间:** <时间戳>
**视角数量:** <N>
**采纳的修改:** <列表>
**忽略的建议:** <列表 + 忽略理由>
**遗留问题:** <列表 + 处理方式>
```

6. **交给用户:** 把修改后的 Spec / Plan + 审查记录一并交给用户批准

## 关键边界

- 子代理**不能**修改 Spec / Plan,只能返回评论
- 主 Agent **不能**把子代理评论原样转给用户,必须经过整合判断
- 对抗性审查**不替代**用户审批;用户仍是最终决定者
- 审查**不阻塞**流程,主 Agent 整合完即可继续;不需要等子代理结果出来才能进入下一步规划

## 常见错误

- 把每个视角都跑一遍(2-3 个足够,超过 3 个收益递减)
- 让子代理修改 Spec / Plan(违反权限边界)
- 把子代理评论原样复制给用户(用户看到的是噪音,不是决策)
- 跳过主 Agent 的整合判断,直接采用所有建议(失去主 Agent 价值)
- 对抗性审查完成后直接进入执行(必须等用户批准)
- 对轻量或中等任务也跑对抗性审查(过度工程,违反第一性原理)
