# 业务驱动开发

## 不要进入本 Skill

- 清晰、局部、可逆的代码修改 → 走 `$ep-code-change`
- 跨上下文且仍模糊的大目标 → 走 `$ep-large-project`
- 已有批准 Spec 和主 Plan → 走 `$ep-execution`
- 活跃业务故障 → 走 `$ep-diagnosis`
- 只是想"看看大致实现清单" → 直接拒绝,先做业务调查

## 入口检查

- [ ] 单一业务功能/模块,目标与边界基本清晰
- [ ] 可以在一个规划会话内形成可批准 Spec
- [ ] 用户明确要求规划（不自动触发）
- [ ] 没有更好的入口（外部请求走 `$ep-request-intake`,跨上下文走 `$ep-large-project`,活跃故障走 `$ep-diagnosis`）

## 输出契约

- Spec（业务规格）：业务目标 + 参与者 + 验收契约 + 范围外（待用户批准）
- 主 Plan：业务切片 + 依赖图 + Frontier + 核心闭环 + 自主边界（待用户批准）
- 验收依据：每条业务规则有可观察结果
- 全局进度区,让用户能从 Plan 文件直接看到整体进展
- 详细协议见 [spec-protocol.md](references/spec-protocol.md)、[plan-protocol.md](references/plan-protocol.md)

## 核心原则

以可验收的业务闭环作为规划、实现和验证的基本单位。先与用户确认并批准 Spec（业务规格）和主 Plan（主执行计划），再自主完成授权范围；不要用技术任务、测试数量或代码完成度代替业务结果。

Agent 不是被动的执行者。用户提出需求或方案时，Agent 应当先理解用户的真实目标，主动评估方案是否最优，存在更好的替代方案时主动提出并说明理由，然后由用户决定。

**第一性原理：默认只解决已确认的核心业务路径和已验证场景。** 边缘场景必须识别并列出（防止漏掉），但默认不实现、不进 Spec 主线、不进验收标准。出现"以后可能用到"的扩展性假设时直接砍掉，等真实需求出现再加；不为尚未发生的负载、租户、规模或迁移预留方案。

本 Skill 只在用户显式调用时运行。事实可从仓库和工具获取时直接调查；业务决策由用户确认；可逆且不改变业务契约的实现选择交给 Agent（执行代理）。

## 工作流

### 1. 编写 Spec

读取 [spec-protocol.md](references/spec-protocol.md)。探索现有系统后，与用户逐项确定：

- 业务目标、参与者和范围；
- 最小业务闭环；
- 业务规则、不变量和验收依据；
- 已纳入本次交付的增强能力；
- 质量属性和关键技术决策。

每次只讨论一个决策，并给出推荐答案。用户提出具体方案时，先评估该方案是否最优，有更好的替代方案时主动提出。重要用户路径、信息层级或产品形态尚不明确时，明确调用 `$ep-product-design`；必须运行、操作或展示后才能判断时，明确调用 `$ep-prototyping`；依赖外部事实时调用 `$ep-research`；业务术语、场景、边界或不变量存在多种解释时调用 `$ep-domain-modeling`；涉及公共接口、计算、存储、迁移或系统结构的重要取舍时，明确调用 `$ep-architecture`。写入 `docs/easypower/<feature>/spec.md`，等待用户明确批准。

### 2. 编写渐进式 Plan

Spec 批准后读取 [plan-protocol.md](references/plan-protocol.md)。创建短小的 `plan.md` 作为执行地图，定义业务切片、依赖图、核心闭环里程碑、验收证据和自主执行边界。主 Plan 必须包含全局进度区，让用户在批准时就能看到完整的切片总数和预期路径。

大型工作只详细展开第一个可执行子 Plan；其他子 Plan 先保留目标、依赖和验收结果。Plan 可包含固定重要决策所必需的最小代码、伪代码、Schema 或接口，不提前书写普通实现。等待用户明确批准主 Plan。

### 2.5 对抗性审查（仅重度规模触发）

主 Plan 写完后、用户审批前，主 Agent **并行 spawn 多个只读子代理**对 Spec 和主 Plan 做对抗性审查。每个子代理带一个固定的视角 Prompt，从不同立场独立判断。读取 [adversarial-review.md](references/adversarial-review.md) 获取标准视角和整合协议。

**触发条件：** 任务规模属于重度（跨切片、跨上下文、复杂业务闭环），且 Spec/Plan 涉及公共契约、跨模块依赖或不可逆决定。

**默认视角（按场景选 2-3 个）：**
- 产品经理（PM）：用户路径是否成立、范围是否有遗漏/越界、验收标准是否对用户可观察
- 架构师：公共接口、计算、存储、迁移是否合理，是否存在更简单方案
- 用户代表：高频任务的摩擦点、边界场景的体验假设、信息层级
- QA / 验证：业务规则是否都有可观察验收、不变量是否能实际验证

**关键边界：**
- 子代理只能返回评论和建议，不直接修改 Spec / Plan
- 主 Agent 整合评论，**主动决定**是否需要修改后再交给用户
- 不要把子代理评论原样复制给用户；分类、去重、判断采纳与否
- 对抗性审查不替代用户审批；用户仍拥有最终决定权

### 3. 自主执行

Plan 批准后，明确调用 `$ep-execution`，传递 Spec 和主 Plan 的路径。规划会话在此完成；执行 Skill 使用全新上下文恢复磁盘事实、展开子 Plan、调度子代理和交付业务证据。

如果当前环境没有 `ep-execution`，停止并说明缺少执行能力，不在本 Skill 中临时重建另一套执行流程。

### 4. 升级审批

以下情况暂停受影响任务并请求用户决定：

- 改变业务范围、验收标准或业务不变量；
- 改变已批准的公共接口、数据模型或关键架构；
- 缺少凭据、外部权限或不可恢复操作授权；
- 现有证据无法区分多个业务解释；
- 失败暴露出主 Plan 未覆盖的系统性风险。

仅细化实现步骤、修正局部缺陷或选择等价实现，不重新请求审批。

### 5. 交付报告

按 Spec 的业务目标报告核心闭环、增强项、证据、偏差、剩余风险和产物位置。使用“哪个业务场景通过了什么证据”，不要只报告测试命令为绿色。

## 快速判断

| 问题 | 归属 |
|---|---|
| 为什么做、做成什么、如何验收 | Spec |
| 按什么业务切片和依赖顺序交付 | 主 Plan |
| 当前切片如何实现和验证 | 子 Plan |
| 普通编码细节 | 执行 Agent |
| 新的业务或关键架构决策 | 升级给用户 |

## 常见错误

- 把数据库、后端、前端、测试拆成互不交付业务价值的水平任务。
- 在 Spec 中替用户决定尚未确认的角色、阈值或业务口径。
- 一开始写完所有子 Plan，导致后续计划依赖过期代码。
- 对同一业务结果在每个代码层重复测试。
- 核心闭环未通过就开始性能、交互或存储增强。
- 子代理发现重大歧义后自行选择一种解释继续执行。
- 在执行中新建独立的 Plan 文件来替代已批准的主 Plan；应原地修改并在变更日志中记录。
- 主 Plan 不包含全局进度区，让用户无法从 Plan 文件中直接看到整体进展。
- 自行发明硬性能指标（如“接口响应时间必须在 X 秒内”），用户没有提出时不应设定。
- 只服从用户指令而不提供专业判断；用户的方案明显存在更优解时应主动提出。
- 把"可能用到"的边缘场景自动塞进 Spec 主线，付出与价值不匹配的复杂度。
- 为尚未发生的负载/租户/迁移预留架构方案，而不是按"现在简单、以后再升级"处理。
