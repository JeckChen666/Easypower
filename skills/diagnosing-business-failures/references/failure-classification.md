# 业务失败分类

先分类，再决定诊断路径和审批边界。

| 类型 | 判定线索 | 处理 |
|---|---|---|
| 实现缺陷 | 已批准业务契约明确，代码或配置首次产生错误 | 建反馈环，追踪并在授权内修复 |
| 输入或数据质量 | 源数据缺失、重复、非法或版本错误 | 隔离数据，确认责任边界和补偿方式 |
| 环境或外部依赖 | 只在特定版本、配置、区域、供应商或资源状态出现 | 固定环境差异，验证失败语义和恢复路径 |
| 验收工具失真 | 黄金文件、测试、监控或查询本身不能可靠判定结果 | 先修复证据链，不得标记业务已恢复 |
| 业务口径多解 | Spec 和证据支持两种以上合理结果 | Blocked，列出选项和影响，等待批准 |
| 性能退化 | 结果正确，但代表性业务场景的资源或时延恶化 | 固定负载，分解瓶颈，证明结果等价 |

## 失败记录

```markdown
## 业务失败
**业务场景与参与者：**
**预期结果及依据：**
**实际结果：**
**影响、频率与时间窗：**
**输入/数据版本：**
**实现/配置/环境版本：**
**当前风险与止损：**
**反馈入口：**
```

错误消息、测试名和技术指标是辅助信息。失败记录的主语应是业务场景，例如“同一支付意图发生两次成功扣款”，而不是“出现两条请求日志”。

## 升级条件

- 证据无法区分业务解释；
- 修复需要改变已批准契约、共享 Schema 或关键架构；
- 涉及生产写操作、不可恢复动作、补偿或退款；
- 缺少必要数据、权限或外部系统事实；
- 反馈工具不可靠，无法证明恢复。

一个故障阻塞时，只暂停依赖其证据或契约的切片；无关执行前沿可以继续。
