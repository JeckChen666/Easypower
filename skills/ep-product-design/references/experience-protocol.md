# Product Experience Contract（产品体验契约）

体验契约是 Spec 的按需组成部分，记录用户如何完成重要任务以及如何证明操作路径可用。它不替代业务目标、架构设计或 UI 生产实现。

## 证据等级

| 等级 | 示例 | 使用方式 |
|---|---|---|
| 用户行为证据 | 访谈、可用性观察、埋点、录屏、工单 | 可以支持用户问题判断 |
| 项目事实 | 当前页面、权限、数据结构、性能和合规约束 | 可以约束候选方案 |
| 业务方陈述 | 目标用户、流程、优先级和已知问题 | 由用户确认后作为业务输入 |
| Assumption（待验证假设） | Agent 推断的习惯、偏好和认知 | 必须显式标记并安排验证 |

Agent 角色和通用 UX Heuristic（体验启发式原则）只能帮助发现问题，不能把假设升级为用户事实。

## 任务走查

每个候选方案使用同一组任务和数据。至少记录：

- 用户起点、目标和完成标志；
- 必须理解的信息和作出的决定；
- 操作步骤、往返、等待和重复输入；
- 当前条件、进度和结果是否始终可见；
- Empty（空状态）、Loading（加载状态）、Error（错误状态）、Permission（权限状态）和 Partial Success（部分成功）状态；
- 误操作后的撤销、恢复或求助路径；
- 桌面、窄屏、键盘或辅助技术等真实环境约束。

不使用固定“点击数越少越好”代替判断。高风险动作可以需要确认，高频低风险动作应减少重复劳动。

## 候选方案比较

只比较会改变用户任务的方案。每个方案说明：

| 维度 | 需要回答的问题 |
|---|---|
| 用户价值 | 是否更容易完成最重要的任务 |
| 可理解性 | 用户能否判断当前位置、可做动作和结果 |
| 操作效率 | 高频任务是否减少等待、往返和重复输入 |
| 错误恢复 | 失败、权限不足和误操作是否可理解、可恢复 |
| 业务适配 | 是否支持批准的规则、范围和优先级 |
| 技术约束 | 性能、数据、权限和演进代价是否可接受 |
| 可验证性 | 能否通过走查、原型或真实用户观察验证 |

无法靠文字可靠比较时，把唯一决策问题、候选答案、观察场景和判定标准交给 `$ep-prototyping`。

## 模板

```markdown
# <功能名称> Product Experience

**状态：** 草案 | 已批准
**Spec：** <链接>

## 用户与证据
### 主要用户和环境
### 已有用户证据
### 待验证假设

## 关键任务
| 任务 | 频率/重要性 | 起点 | 完成标志 | 当前阻力 |
|---|---|---|---|---|

## 候选产品形态
### 方案 A
### 方案 B
### 方案 C（按需）

## 任务走查与关键状态
记录相同任务下的路径、信息、反馈、异常和恢复。

## 推荐与取舍
说明推荐、用户价值、业务代价、技术约束和推翻条件。

## 用户决定
记录批准、拒绝或要求验证的方向。

## 回写 Spec
列出需要进入产品体验、验收契约、质量属性和范围的稳定结论。
```

简单功能不创建独立文件，直接将必要内容写入 Spec。复杂功能的 `experience.md` 在批准后只保留调查证据和方案比较，稳定规则以 Spec 为准。
