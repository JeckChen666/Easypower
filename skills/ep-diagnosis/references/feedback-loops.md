# Feedback Loop（业务反馈闭环）

反馈闭环必须能直接判断用户报告的问题，并可在修复前后重复运行。

## 选择顺序

| 业务故障 | 优先反馈方式 |
|---|---|
| 计算或转换错误 | 同一输入对 Golden Result（基准结果）、旧版本或业务不变量做差异 |
| 接口行为错误 | 固定请求、身份和状态，断言业务响应与副作用 |
| UI（用户界面）流程错误 | 驱动关键路径，检查 DOM（文档对象模型）、网络和最终业务状态 |
| 数据或消息问题 | 重放捕获事件，核对状态转换和幂等副作用 |
| 低概率时序问题 | 可控屏障、故障注入或高重复率循环 |
| 性能退化 | 固定数据、查询分布、并发和环境的基准与 Profiler |
| 版本回归 | 同一输入或产物在已知正常版本与失败版本上做差分或二分 |

优先复用已有业务验收和生产材料。只有现有证据不能稳定判断旧缺陷时才新建测试。

## 质量检查

一个可用的反馈闭环应满足：

- **症状一致**：失败与用户报告的业务结果相同；
- **可判定**：有明确预期，不是“没有崩溃”；
- **足够稳定**：确定性问题重复一致，偶发问题的触发率足以比较；
- **成本合适**：优先选择能在数秒内完成的局部反馈闭环，必要时保留较慢的原始业务复验；
- **可由 Agent 运行**：命令、输入、环境和输出可保存。

反馈命令可以是测试、CLI、HTTP 脚本、浏览器流程、数据查询或基准。测试框架不是必需条件。

## 无法复现

不能本地复现时，不要用代码阅读代替证据。按成本依次争取：

1. 原始输入、请求、事件、HAR（浏览器网络归档）、日志、查询计划或错误数据快照；
2. 脱敏生产数据或请求的离线重放；
3. 临时、带唯一标识且可清理的边界观测日志；
4. 只读生产副本或受控灰度验证；
5. 明确的人机协作复现步骤。

记录尝试过的入口、失败原因和仍缺少的事实。无法获得稳定的失败信号时，可以做风险控制和取证，但不能宣称根因或修复完成。

## 缩小复现

每次只删除或固定一个因素：记录、字段、调用者、配置、权限、时间、并发、依赖或版本。缩小后必须重新确认仍是同一个业务症状。最小复现用于减少假设空间，不要求删除业务症状成立所必需的真实边界。
