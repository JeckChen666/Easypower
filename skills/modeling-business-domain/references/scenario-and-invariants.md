# 场景与不变量协议

## 先用场景，后下定义

抽象名词可以掩盖分歧。选择能让两种解释产生不同业务结果的最小场景：

```markdown
### <场景名称>
Given <已知业务状态>
When <参与者执行动作或发生事件>
Then <用户或业务可观察结果>

**它区分的问题：** <候选解释 A 与 B>
**结论：** 已确认 | 候选 | 阻塞
```

一个场景只承担一个主要区分目标。无需把所有排列组合都写出来；优先选择最可能改变模型的边界。

## 场景选择

至少从与当前歧义有关的类型中选择：

| 类型 | 用途 |
|---|---|
| 核心成功 | 证明主要业务闭环中的概念关系 |
| 相邻概念 | 证明两个相似术语不是同一个对象或动作 |
| 失败与撤销 | 证明失败、取消、回退是否改变既有业务事实 |
| 生命周期 | 证明创建、激活、停用、删除是否属于不同状态 |
| 作用域 | 证明租户、项目、角色、地区或时间范围是否隔离 |
| 并发与历史 | 证明重复动作、晚到结果和审计历史如何处理 |

## 提炼不变量

不变量应满足：

- 跨多个业务场景始终成立；
- 违反时会产生错误业务结果；
- 不依赖数据库、框架或具体算法；
- 可以由业务例子或可观察证据验证。

使用“必须、最多、不得、只有……才……”表达边界。把来源、适用范围和反例一起记录。暂未确认的规则标为候选，不伪装成事实。

不属于领域不变量的例子：必须使用某数据库；DTO 必须不可变；缓存 TTL 是 10 分钟；某类必须实现某接口。这些通常属于架构、配置或实现约束。若 TTL 代表“用户看到的数据不得晚于业务时间 10 分钟”，后者才是业务质量属性。

## 报表领域示例

“报表版本”可能混合定义修订、计算运行、结果快照和发布记录。用以下场景拆分：

```markdown
Given 当前发布指向结果快照 R1
When 重算成功并生成结果快照 R2，但尚未发布
Then 用户仍看到 R1

Given 当前发布指向 R2
When 用户执行回退
Then 系统新增一条指向 R1 的发布记录，R2 和历史记录不被覆盖
```

这些场景可以支持“保存结果不等于发布”和“回退追加历史而非改写历史”等候选不变量，但是否成为业务规则仍需用户确认。它们不要求领域阶段设计结果表字段或发布事务实现。
