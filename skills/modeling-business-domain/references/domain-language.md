# 领域语言协议

## 选择术语

只有术语同时满足以下条件时才进入稳定词汇表：

- 属于当前业务领域，而非通用编程概念；
- 不明确会导致需求、规则或验收出现不同解释；
- 已通过具体场景确认含义和边界；
- 业务方可以自然使用并区分它。

不要追求收录所有名词。页面标签、一次性项目用语和从代码即可读懂的实现名词通常不需要领域定义。

## 消除重载词

处理“账号”“版本”“状态”“用户”“管理员”等重载词时：

1. 收集它在当前材料中的所有具体用法；
2. 为含义不同的用法分别提出候选规范词；
3. 用一个会让候选含义产生不同结果的场景验证；
4. 由用户确认业务含义；
5. 将旧词列入 `_Avoid_`，但保留迁移线索。

不要只做同义词替换。例如“账号”可能分别指登录身份、租户、租户成员或项目成员关系，它们的生命周期和权限范围不同。

## `CONTEXT.md` 格式

单一上下文默认使用项目根目录的 `CONTEXT.md`；项目已有其他位置约定时沿用现状。文件只做稳定业务词汇表：

```markdown
# <业务上下文>

<一两句说明该业务区域负责什么。>

## 语言

**租户成员（Tenant Member）**
某个人加入特定租户后形成的成员关系；其资料和租户级状态只在该租户内成立。
_Avoid_: 账号、用户

**登录身份（Identity）**
用于认证并追踪操作者的身份；它不等于任何租户中的成员资格。
_Avoid_: 登录账号、成员
```

定义保持一至两句，说明“它是什么”和关键边界。不要加入字段列表、方法、Schema、技术组件、实现状态、验收条件或任务笔记。

## 冲突处理

现有词汇表、Spec、代码和用户表述不一致时，分别标记来源与现状：

```markdown
**候选目标含义：**
**现有词汇表：**
**代码当前行为：**
**产生不同结果的场景：**
**需要用户决定：**
```

批准后的业务含义进入 Spec 和词汇表；代码差距进入 Plan。不要在领域讨论中顺手完成大规模重命名。
