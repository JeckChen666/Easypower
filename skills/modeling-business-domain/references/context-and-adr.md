# 上下文与 ADR 协议

## 产物职责

| 内容 | 权威位置 |
|---|---|
| 本功能的目标、场景、规则、不变量和验收 | 已批准 Spec |
| 跨功能稳定复用的业务术语 | `CONTEXT.md` 或项目已有词汇表 |
| 多个业务上下文及其语言边界 | `CONTEXT-MAP.md` |
| 少量难以逆转且反直觉的取舍 | 项目已有 ADR 目录 |
| 实现顺序、迁移任务和验证 | Plan |
| 局部命名、字段、普通依赖和参数 | 代码、配置、提交或评审记录 |

同一事实只保留一个权威来源，其他位置使用链接或简短引用。文件按需创建；没有稳定术语就不创建 `CONTEXT.md`，没有真实多上下文就不创建 `CONTEXT-MAP.md`，没有合格决定就不创建 ADR。

## 多上下文准入

仅当同一个词在不同业务区域具有不同含义、规则和生命周期，且边界需要长期协作时，使用 `CONTEXT-MAP.md`：

```markdown
# Context Map

## 上下文

- **订购**（`src/ordering/CONTEXT.md`）：接收并跟踪客户订单
- **结算**（`src/billing/CONTEXT.md`）：生成应收并处理付款

## 关系

- **订购 -> 结算**：订单达到可结算条件后传递订单标识和金额事实。
```

关系描述业务责任、交换事实和所有权。不要把部署拓扑、类依赖或表关联伪装成上下文地图。

## ADR 三条件

只有以下三个条件同时成立才创建 ADR：

1. **难以逆转**：未来改变会带来显著迁移、兼容或组织成本；
2. **脱离背景会令人意外**：后来者仅看代码无法理解为什么这样做；
3. **存在真实取舍**：至少有一个可行替代方案，并因具体理由被放弃。

变量命名、普通库、局部缓存 TTL、常规参数和显而易见的实现选择通常不满足三个条件。若一个技术选择确实达到准入条件，将架构比较交给 `$designing-business-architecture`；本 Skill 只判断领域边界决定是否需要长期记录。

## 最小 ADR

沿用项目已有位置、编号和格式。没有约定时使用 `docs/adr/NNNN-<slug>.md`：

```markdown
# <决定标题>

<一至三句说明背景、决定和理由。>
```

仅在确有价值时增加状态、备选方案、后果和失效条件。不要为统一模板填满空洞章节，也不要复制 Spec 或完整讨论历史。

适合记录：跨上下文的数据所有权；难以替换的集成模式；反直觉但有约束依据的业务边界。

不适合记录：`member` 变量名；日期格式库；可随时调整的缓存参数；普通 CRUD 形态；已由 Spec 明确且无需解释取舍的规则。
