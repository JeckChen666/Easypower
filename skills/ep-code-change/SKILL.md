# 轻量代码修改

## 先判断规模

满足以下条件时按 Quick Change（快速修改）直接完成：

- 目标和正确结果清楚；
- 检查代码后确认影响范围局部；
- 沿用现有业务规则、接口和架构；
- 没有需要用户选择的新业务口径；
- 修改可恢复，且能在当前上下文完成。

不要按敏感词机械升级。为指定用户赋予明确权限、修正一个确定数值、调整已确认公式或纠正明确状态，都可以是 Quick Change，前提是对象、结果、授权和影响范围清楚。该判断不扩大生产写入、不可恢复操作或外部权限的授权。

目标不清、需要定义或改变业务规则、影响公共接口或 Schema、涉及跨模块迁移、影响范围无法确认，或者需要跨上下文和多个 Agent 时，停止直接修改并明确调用 `$ep-use-easypower`。说明已知事实和升级原因，只交接一次。

## 快速完成

1. 读取相关代码和项目约定；
2. 做满足目标的最小完整修改，不顺带重构；
3. 默认执行工程基本实践：查询条件加索引、列表接口分页、不在列表查询中返回大体积字段、参数化查询；
4. 默认不新增测试用例；
5. 已有测试覆盖被修改行为时，同步修改必要用例并运行最相关的测试，不删除、弱化或绕过原有保护；
6. 使用成本最低的直接证据检查结果，例如 diff、类型检查、局部运行或页面观察；
7. 简要报告修改、验证和未检查内容。

测试期望只有在用户要求的行为确实改变时才能更新，不要为了让测试通过而接受错误结果。用户明确要求新增测试或更广验证时，按用户要求执行。

## 优先级

用户已经明确调用 `$ep-use-easypower` 或其他具体 Easypower Skill 时，让该流程拥有控制权，不降低它的验证要求。由 `$ep-use-easypower` 选择本 Skill 时直接执行 Quick Change，不再路由回去。

## 主动评估

用户提出具体方案时，先评估是否是实现目标的最优途径。存在更简单、更健壮或更合理的替代方案时，主动提出并说明理由，由用户决定。即使是 Quick Change，Agent 也不应只是机械地执行用户描述的步骤。

## 代码注释

注释密度应当匹配代码的生命周期和重要性,而不是统一要求：

| 场景 | 注释要求 |
|---|---|
| 一次性脚本、调试代码、临时工具 | 不强制注释;代码本身说明意图即可 |
| 业务核心逻辑（领域规则、状态判断、计算口径） | 详细注释每一条规则的"为什么",目标:接手者不需要问业务方就能读懂 |
| 复杂算法或非直觉实现 | 逐步解释思路,不要只写结果 |
| 公共接口和关键函数 | 参数含义、返回值语义、异常行为和调用前提 |
| 普通 CRUD 和样板代码 | 简洁,不冗余注释显而易见的操作 |

**判断标准:** 这段代码三个月后还会被读吗?会 → 注释;不会 → 简洁即可。

**"业务核心逻辑"的判定:** 修改它会改变业务结果(数值、权限、状态、对外契约)的代码。不是"包含业务关键词"的代码。

业务核心逻辑的注释密度没有上限,宁可注释过多,也不要让业务意图藏在代码里。

## 日志记录

日志强度匹配代码的场景,而不是统一要求:

| 场景 | 日志要求 |
|---|---|
| 一次性脚本、调试代码 | `print` 没问题,无需标准日志框架 |
| 业务核心场景 | 必须使用语言标准日志框架(如 Python `logging`、Java `slf4j`/`logback`),记录关键输入、状态转换、重要分支、外部调用结果 |
| 业务异常捕获 | 记录完整堆栈信息和触发时的关键数据(用户 ID、订单号、TraceID),确保仅凭日志能定位问题 |
| 普通 CRUD、样板代码 | 默认日志已足够,不重复记录 |

**判断标准:** 这段代码生产环境会出现吗?会 → 标准日志框架 + 充分上下文;不会 → 简洁即可。
