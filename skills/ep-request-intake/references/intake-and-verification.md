# 请求调查与验证协议

## 请求事实表

```markdown
**来源：**
**提交者/受影响角色：**
**候选类别：**
**观察到的现象：**
**期望业务结果：**
**建议方案：**
**声称的影响/紧迫性：**
**已有证据：**
**项目调查：**
**仍属未知：**
```

观察、期望和方案必须分栏。业务方说“必须上 Kafka”只能证明他们提出了一个方案；在负载、时效和瓶颈有证据前，不能证明流式架构是需求。

## 项目调查顺序

1. 读取请求全文、附件和历史处理记录；
2. 查找相关业务术语、Spec、ADR、帮助文档和产品入口；
3. 按领域概念搜索现有能力与相邻行为；
4. 检查活动请求、已批准计划、关闭原因和长期范围决定；
5. 检查当前实现和运行证据是否支持主张；
6. 只对仍会改变分流结论的空白请求补充信息。

搜索不到只是“未发现”，不是“不存在”。记录查过的范围，避免下一会话重复调查。

## 缺陷验证

使用最小证据链。字段含义为 Given（前提）、When（动作）、Then（预期）、Actual（实际）和 Evidence（证据）：

```markdown
Given <业务前提和输入>
When <用户动作或系统事件>
Then <业务契约期望>
Actual <实际结果和差异>
Evidence <样本、日志、截图、关联 ID 或运行记录>
```

优先复用报告者的真实样本并脱敏。验证范围由风险决定：计算差异检查 Golden Result（基准结果）；权限检查允许/拒绝矩阵；状态问题检查转换；间歇故障使用时间窗和关联 ID；PR 对照声称行为检查 diff，并运行针对性验证。

验证失败有三种不同结论：

- **主张未成立**：相同条件下实际符合契约，保留证据并检查环境差异；
- **信息不足**：无法构造相同条件，进入 `Needs Evidence`；
- **契约未知**：实际行为明确，但业务方尚未确认期望，进入 `Needs Business Decision`。

不要把“没复现”直接写成“没有问题”，也不要在 Triage 阶段猜测根因并修改代码。

## 增强验证

至少回答：谁在哪个决策或操作中受阻；当前替代路径是什么；频率和影响如何；期望结果是什么；不做的后果是什么；已有能力为何不够。

方案评估留给 Spec、Prototype 或 Architecture。Triage 可以指出“现有查询优化可能比新平台更小”，但不应在业务问题未确认时完成技术选型。

## 紧急边界

出现持续金额错误、越权、敏感数据暴露、数据损坏或广泛不可用时，先确认影响是否正在发生。若是，最小化外部写入，保存证据并显式转交 `$ep-diagnosis`；普通 Brief 可在止损后补齐。
