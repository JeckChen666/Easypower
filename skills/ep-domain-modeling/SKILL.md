# 业务领域建模

## 不要进入本 Skill

- 术语清晰、无歧义 → 直接写 Spec
- 只是数据库表/类名/字段定义 → 留给执行 Agent
- 想把所有业务名词都塞进词汇表 → 直接拒绝
- 还没有真实业务场景验证就建模 → 等具体场景

## 入口检查

- [ ] 至少有一个术语/边界/不变量存在多种合理解释
- [ ] 解释错误会改变业务结果（数值、权限、状态、契约）
- [ ] 能用具体 Given/When/Then 场景验证边界
- [ ] 没有更好的入口（外部事实走 `$ep-research`,长期架构走 `$ep-architecture`）

## 输出契约

- 规范术语清单（每个术语的内涵/外延/适用上下文）
- 关键场景 + 反例（Given/When/Then）
- 不变量清单（描述业务结果,不绑定实现）
- ADR 仅在"难以逆转 + 脱离背景会意外 + 存在真实取舍"三个条件都满足时创建
- 详细协议见 [domain-language.md](references/domain-language.md)、[scenario-and-invariants.md](references/scenario-and-invariants.md)、[context-and-adr.md](references/context-and-adr.md)

## 核心原则

领域建模用于消除会导致不同业务解释的歧义。用具体场景明确概念、边界和规则，再把已确认结论回写业务事实的权威来源；不要把领域模型提前变成实体类、数据库表或通用架构设计。

本 Skill 只处理当前决策所需的最小模型。没有业务歧义时返回上游，不为完整而补齐无关术语、图表或文档。

## 1. 明确要解决的歧义

明确当前业务问题、涉及的参与者、模糊术语、可能的不同解释，以及解释错误会影响的业务结果。读取现有 Spec（业务规格）、业务文档、`CONTEXT.md`、`CONTEXT-MAP.md`、相关代码和已有 ADR（架构决策记录）。

区分三类信息：

- 用户确认的业务含义与取舍；
- 代码、数据和现有文档呈现的项目事实；
- Agent（智能体）为暴露边界提出的候选概念和场景。

代码与业务说法冲突时，展示具体差异并请用户决定哪一个应成为目标规则。不要静默让代码定义业务，也不要把用户的新说法直接当作现有行为。

## 2. 建立最小业务语言

读取 [domain-language.md](references/domain-language.md)。对每个重载词提出少量互斥的规范术语，并说明每个术语指什么、不指什么、在哪个上下文成立。优先使用业务方能自然复述的名称。

只记录本领域特有且会影响业务理解的概念。数据库、缓存、异常、DTO 等通用实现概念不进入业务词汇表。术语确定前不要批量改代码或文档。

## 3. 用场景验证边界

读取 [scenario-and-invariants.md](references/scenario-and-invariants.md)。构造最少但有区分力的具体场景，优先覆盖：

- 正常成功路径；
- 容易混淆的相邻概念；
- 生命周期变化、撤销或失败；
- 权限、时间、租户或作用域边界；
- 两种解释会产生不同结果的反例。

对每个场景写清 Given（前提）、When（动作）、Then（结果），并用业务可观察结果判断候选模型。只有多个场景都必须遵守的规则才提升为不变量；不要把当前实现方式包装成业务不变量。

## 4. 确认边界与责任

明确概念的身份、生命周期、所有者、作用域和关系。多个业务区域对同一个词有不同含义时，分别命名并说明转换或协作关系。

只有系统确实存在多个独立语言和模型边界时才建立上下文地图。按团队目录、微服务或数据库数量机械切分，不足以证明存在多个业务上下文。涉及系统结构或集成方式的重要取舍时，将问题交给 `$ep-architecture`。

## 5. 只保留必要的权威产物

读取 [context-and-adr.md](references/context-and-adr.md)，并遵循项目已有约定：

- 业务规则、场景、不变量和验收结果回写 Spec；
- 稳定的规范术语按需写入 `CONTEXT.md`；
- 多上下文关系只有真实需要时写入 `CONTEXT-MAP.md`；
- ADR 仅记录同时满足“难以逆转、脱离背景会令人意外、存在真实取舍”的决定；
- 实现步骤、字段、类、普通库和局部参数留给 Plan、代码、配置或评审记录。

不要同时创建 Glossary（词汇表）、Domain Model（领域模型）、Decision Log（决策记录）和说明文档来保存同一结论。用户批准前标记候选含义；批准后再更新权威文件，并列出受影响但尚未迁移的旧用语。

## 6. 返回上游

输出一份可直接批准的短结论：

1. 已解决的歧义和规范术语；
2. 证明边界的关键场景与反例；
3. 已确认的不变量；
4. 与现有代码或文档的冲突；
5. 写入 Spec、上下文词汇表或 ADR 的内容；
6. 仍会阻止 Spec 或 Plan 批准的问题。

用户确认后，将业务结论交回 `$ep-planning`。领域建模不接管 Plan 或生产实现。

## 完成条件

- 每个关键术语只有一个当前上下文内的明确含义；
- 关键关系由具体场景和反例验证，而非只靠名词列表；
- 不变量描述业务必须成立的结果，不绑定偶然实现；
- 业务语言、Spec、代码现状之间的冲突已解决或明确阻塞；
- 产物各有唯一职责，没有领域文档膨胀；
- ADR 准入三个条件全部满足，否则不创建；
- 用户已确认会影响业务口径、边界或规则的选择。

## 常见错误

- 把一个重载词直接替换成另一个词，却没有拆开不同概念。
- 只讨论抽象实体关系，不用失败、撤销、跨作用域等场景验证。
- 从数据库表或现有类名反推业务必须如何运作。
- 在领域模型中提前设计字段、接口、继承和存储方案。
- 把所有业务名词都放进词汇表，或把 `CONTEXT.md` 写成第二份 Spec。
- 为变量命名、普通依赖、缓存 TTL 或每个小决定创建 ADR。
- 未经用户确认就批量重命名代码和文档。
