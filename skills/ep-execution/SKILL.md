# 执行业务计划

## 核心原则

只执行已经批准的业务契约。以磁盘中的 Spec（业务规格）、主 Plan（主执行计划）、子 Plan、代码和证据为准，不依赖上一段对话或 Agent（智能体）记忆。业务切片通过验收并留下证据后才算完成。

## 1. 启动检查

读取 Spec 和主 Plan 的完整文件，确认：

- 两者状态均为“已批准”或“执行中”；
- 核心业务闭环、切片依赖、验收摘要和自主执行边界存在；
- 当前仓库、环境、权限和基线可用；
- 没有需要用户先决定的阻塞问题。

任何前提不成立时不要开始实现。报告缺口并停在规划阶段。

## 2. 恢复执行状态

读取 [execution-state.md](references/execution-state.md)。以主 Plan 的状态表为执行账本，结合 Git 状态、子 Plan 和 `evidence/` 目录恢复真实进度。不要因为进程中断就重跑已验证任务，也不要把“代码存在”推断为“业务已经通过”。

根据依赖关系更新 Frontier（当前可执行任务）。优先领取核心业务闭环；核心业务闭环验收通过前不推进纯增强切片。

## 3. 按需展开子 Plan

一个切片即将进入 `Ready（可领取）` 时，根据最新代码展开或刷新对应子 Plan。细化实现步骤不需要重新审批；改变业务范围、验收、不变量、公共接口、数据模型或关键架构时，将切片标为 `Blocked（受阻）` 并升级审批。

## 4. 调度任务

读取 [agent-brief.md](references/agent-brief.md)。由协调 Agent 独占主 Plan、Spec 和跨切片公共契约的写权限。执行 Agent 只接收当前切片所需的事实链接、依赖产物、所有权、完成定义和升级条件。

只有任务之间不存在顺序依赖、公共契约争用、共享状态冲突和文件所有权重叠时才并行。存在共享接口或 Schema 时，先建立并完成契约冻结切片，或将相关任务串行化。

环境不支持子代理时，保持同一切片和状态协议顺序执行，不伪造独立代理或并行结果。

展开或刷新子 Plan 是协调 Agent 的自主行为，不需要中断用户等待审批。用户批准主 Plan 时已经授权了全部切片的目标和验收；子 Plan 只是将授权展开为实施细节。只有当展开过程发现必须改变已批准契约时才升级（见第 7 节）。

## 5. 完成切片循环

对每个已领取切片：

1. 确认基线和依赖证据仍然有效；
2. 实现最小完整业务路径；
3. 对业务核心逻辑添加详细注释：每一条业务规则、状态判断和计算逻辑都要注释清楚"为什么"，目标是让新接手的人不需要询问业务方就能读懂代码；
4. 补充充分的日志记录：使用语言标准日志框架，核心业务场景宁多勿少，确保包含足够上下文以供错误排查；
5. 保存实现摘要和局部检查结果，将状态改为 `Implemented（已实现）`；
6. 按 [validation-and-recovery.md](references/validation-and-recovery.md) 选择最少但充分的业务验证；
7. 回归已经成立的核心业务证据；
8. 验证通过后保存证据并改为 `Verified（验证）`；
9. 核心闭环、高风险切片、公共契约变化或最终交付明确调用 `$ep-delivery-review`；评审通过后进入 `Completed（已完成）`；
10. 低风险且已有直接证据的切片不强制独立评审，可以从 Verified 进入 Completed；
11. 根据依赖关系更新 Frontier 并调度下一批任务。

不要为每个切片固定运行全量测试、双阶段评审或独立审查代理。验证和评审强度由业务风险、影响范围和证据可信度决定。

## 6. 切片完成汇报

每个切片状态变为 Completed 后，立即向用户输出进度汇报，同时更新主 Plan 的全局进度区。汇报格式：

```
进度汇报 -- <切片ID> <切片名称>
全局进度：X/Y 切片已完成（Z 个受阻）
当前切片结果：<一句话业务结论>
关键证据：<证据摘要或链接>
下一步：<即将执行的切片> 或 <全部完成，准备交付报告>
需要用户关注：<无 / 具体问题>
```

汇报目的是让用户持续知道全局进度和当前结果，不是请求审批。除非「需要用户关注」中列出了具体问题，否则 Agent 汇报后立即继续执行下一个前沿切片。

以下时机也应向用户汇报：

- 切片进入 Blocked 时：说明阻塞原因、受影响范围和仍可继续的前沿；
- 所有可执行切片结束时：输出完整的业务交付报告（见第 8 节）。

## 7. 处理失败和阻塞

局部实现或业务证据失败时，明确调用 `$ep-diagnosis`，传递 Spec、主 Plan、当前子 Plan、失败记录和证据路径。在 Agent Brief（任务说明）和执行更新中写出 Skill 名称，不要只写“交给诊断执行者”。诊断 Skill 建立 Feedback Loop（反馈闭环）、定位根因并在授权范围内修复；证据表明需要改变已批准契约时停止相关切片，不用临时绕过继续推进。

诊断返回后，由协调 Agent 核对原业务场景、回归证据和剩余风险，再恢复切片状态。止损措施、代码已修改或局部测试通过都不能直接把切片推进为 Completed。

一个切片 Blocked 时，继续执行在依赖、契约、状态和所有权上与它无关的 Frontier 任务。记录受阻原因、影响、候选方案和恢复点，等待用户决定。

## 8. 评审与交付

调用 `$ep-delivery-review` 时传递批准的 Spec、Plan、评审范围、实际代码差异（diff）、产物和证据路径，并在 Agent Brief（任务说明）和执行更新中写出 Skill 名称。评审出现 Blocker（阻断项）或 Important（重要项）时，将相关切片退回 In Progress 或标为 Blocked；修复后只重新验证受影响的评审发现、业务证据和必要回归。

所有可执行切片结束后，按 Spec 输出业务交付报告：

- 核心业务闭环及证据；
- 每个增强切片的状态和价值；
- Blocked、未开始和范围外项目；
- 计划偏差及审批情况；
- 实际运行的验证和产物位置；
- 用户回来后可以直接继续的恢复点。

需要完整例子时读取 [bi-execution-example.md](references/bi-execution-example.md)。

## 常见错误

- 未检查 Spec/Plan 批准状态就开始编码。
- 把所有 Ready 标签当成并行安全，忽略共享 Schema 和文件所有权。
- 让执行 Agent 修改主 Plan 或公共契约。
- 把 Implemented 当成 Completed。
- 单个切片阻塞后停止所有独立工作。
- 中断恢复时依赖聊天摘要而不是磁盘事实。
- 在切片之间不必要地停下来等待用户审批；用户批准主 Plan 后，子 Plan 展开和切片推进属于自主范围。
- 切片完成后不汇报进度，让用户无法感知全局状态。
- 用全量测试或代理数量代替业务验收证据。
