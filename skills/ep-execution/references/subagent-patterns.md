# 子代理模式

`ep-execution` 不规定唯一的子代理类型,而是按切片特征选择最合适的模式。下面是四个常用模式,根据切片特征组合使用。

## 模式 A：实现子代理（Implementation）

**用途：** 主要的代码实现工作,典型切片的主体。

**参数：**

- `subagent_type`: `general-purpose`
- `isolation`: `worktree`(大型项目)或不传(小切片)
- `prompt`: [agent-brief.md](agent-brief.md) 模板 + 显式说明「实现 + 验证 + 保存证据」

**特征：**

- 拥有可写文件列表
- 完成后返回实现摘要 + 证据路径
- 升级条件命中时停下,不自行决定

**典型场景：** P01 核心闭环、P02 计算优化、P04 持久化存储

## 模式 B：研究子代理（Research）

**用途：** 在动手实现前先调查外部事实、API 行为或未知依赖。

**参数：**

- `subagent_type`: `Explore`(只读搜索)或 `general-purpose`
- `isolation`: 不传
- `prompt`: 明确要求「只读、不修改任何文件、返回可引用的结论」

**特征：**

- 只读权限,无法修改文件
- 强制使用 WebFetch / WebSearch / Grep / Read
- 返回结构：事实 / 推论 / 未知项

**典型场景：** 调研未知库 API、查证外部服务契约、定位现有代码模式

**与 `$ep-research` 的区别：** `$ep-research` 是 Skill 级别的正式研究流程(进入文档、形成 ADR),研究子代理是切片内部的一次性调查,不形成 Skill 级别产物。

## 模式 C：验证子代理（Verification）

**用途：** 独立验证已实现的切片,提供与实现者不同的视角。

**参数：**

- `subagent_type`: `Explore`(只读)或 `general-purpose`
- `isolation`: 不传
- `prompt`: 明确要求「只读、运行验证命令、不修改代码、返回可信度评估」

**特征：**

- 只读 + 执行权限,不写代码
- 不允许"为了让测试通过而调整断言"
- 返回：业务场景是否通过 / 证据是否可信 / 是否存在未覆盖风险

**典型场景：** 金额计算核验、性能基准对比、复杂公式等价性检查

**何时使用：**

- 高风险切片(金额、权限、状态、公共契约)
- 核心业务闭环验收
- 用户明确要求独立验证

## 模式 D：评审子代理（Review）

**用途：** 评审已完成切片的代码与业务契约一致性。

**参数：**

- `subagent_type`: `general-purpose`
- `isolation`: 不传
- `prompt`: 明确要求「评审,不改代码;按业务契约和工程风险两个维度报告」

**特征：**

- 只读 + 注释权限(可写评审记录,不可改实现)
- 输出 Blocker / Important / Suggestion 三档
- 与 `$ep-delivery-review` 区别:这是切片级别快评审,正式评审仍走 Skill

**典型场景：** 公共契约变化切片、跨模块影响切片、交付前的快速核验

## 组合使用

复杂切片可以组合多个模式:

1. **研究 → 实现 → 验证**：先 spawn 研究子代理,得到结论后再 spawn 实现子代理,完成后用验证子代理独立复核
3. **实现 → 评审**：实现完成后让评审子代理快速看一眼,有问题再走 `$ep-delivery-review`
4. **并行实现 + 串行评审**：两个并行实现子代理完成后再 spawn 评审子代理做集成评审

## 不使用子代理的情况

以下情况不要 spawn 子代理,直接在当前上下文完成:

- < 50 行代码的微调
- 调试 / 一次性验证脚本
- 用户明确要求不分发
- 切片的所有权与主对话共享同一组文件,且改动会立即影响主对话决策

## 常见错误

- 试图让一个子代理承担多个不相关切片的实现 → 应该分开发,每个子代理一个切片
- 让子代理修改主 Plan 或 Spec → 违反所有权边界,协调 Agent 独占
- 不给子代理升级条件 → 子代理遇到歧义会自行决定,污染主对话
- 子代理完成后不在 evidence/ 保存证据 → 切片无法从 Verified 进入 Completed
- 在 Brief 中复制完整 Spec 章节 → 子代理上下文被不必要内容填满
