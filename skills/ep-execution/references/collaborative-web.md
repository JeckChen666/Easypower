# 协同模式 - Web 开发参考

本文件提供协同模式（Collaborative Execution）在 **Web 全栈开发** 场景下的具体参考实现。其他领域（移动端、嵌入式、ML、CLI、库）暂未提供，请完成第一个真实任务后再补充。

## 协同模式的核心目的

**让程序员通过这种模式对自己的代码有非常深刻的印象，相当于代码是自己手写的。**

用户主动选择协同模式的代价是牺牲执行效率，换取代码 ownership 和可追溯性。这是 feature 不是 bug。

## 通用骨架（所有领域都适用）

```
1. 业务规划          （Phase 1 已完成）
2. 数据形态设计      （领域相关）
3. 实体/模型定义     （基于 2）
4. 对外契约定义      （URL/接口/参数/返回值）
5. 契约审查          （写 stub,用户审命名/位置）
6. 契约实现          （填具体逻辑）
7. 调用方联调/集成
```

**协同的颗粒度：**

| 规模 | 颗粒度 |
|---|---|
| 轻量 | 不适用（轻量默认走 `ep-code-change`,无协同） |
| 中等 | 按 Plan 切片审批（3-10 个切片,每个切片整体一次审批） |
| 重度 | 按 Phase 审批（几个切片为一组）；每个切片内部仍自主 |

**关键纪律：**
- 每步完成 → 停下 → 等用户审批 → 才进入下一步
- 用户可能要求在某步反复迭代（接口命名、文件位置、注释风格）
- 用户随时可以要求回退到上一步重新规划
- 协同模式不绕过第一性原理：默认只解决核心闭环,边缘场景识别但不实现

## Web 全栈特化（React + Spring Boot + MySQL）

### 步骤 1：业务规划（已在 `ep-planning` 完成）

主 Plan 已批准。本阶段产出：业务切片清单 + 验收契约。

### 步骤 2：数据库设计

**Agent 输出：** `docs/easypower/<feature>/db-design.md`
- 表清单
- 每张表的字段（字段名、类型、约束、索引）
- 表之间的关系（外键、关联方式）
- 涉及核心业务规则的关键字段（如唯一索引、状态字段、版本号）

**用户审批点：**
- 表的拆分是否合理（是否需要合并/拆分）
- 字段类型和长度是否合理
- 索引设计是否覆盖核心查询
- 是否遗漏了核心业务字段

**不允许：**
- Agent 自行决定命名风格（snake_case vs camelCase）
- Agent 自行添加"以后可能用到"的预留字段
- Agent 自行设计分库分表（除非当前负载已确认）

### 步骤 3：创建实体（Entity）

**Agent 输出：** 对应数据库表的 Entity 类文件
- 字段映射
- 关系注解（OneToMany、ManyToOne 等）
- 主键策略

**用户审批点：**
- Entity 类名和文件位置（`entity/`、`model/`、`domain/`）
- 是否使用 Lombok（@Data / @Getter）
- 关系映射是否符合预期

**不允许：**
- Agent 自行创建额外的 VO/DTO/BO 划分（除非已 Spec 确认）
- Agent 自行添加审计字段（创建时间、修改时间、创建人等），除非业务规则要求

### 步骤 4：页面与接口规划

**Agent 输出：** `docs/easypower/<feature>/api-design.md`
- 页面清单（URL、用途）
- 每个页面的接口清单（HTTP 方法、路径、入参、返回值）
- 接口的业务分组（如订单 CRUD、订单查询）

**用户审批点：**
- 页面划分是否合理
- 接口命名是否清晰（避免用 `getById`、`list`、`save` 这种通用名）
- 接口粒度（是否应该拆分/合并）
- 是否有遗漏的接口（如批量操作、状态切换、删除恢复）

**不允许：**
- Agent 自行设计接口路径风格（`/api/v1/order` vs `/order`）
- Agent 自行添加分页、排序、筛选参数（除非 Spec 已要求）

### 步骤 5：接口定义与审查（写 stub）

**Agent 输出：** Controller 文件，每个接口只写"壳"
- HTTP 方法注解
- URL 路径
- 方法签名（参数、返回值）
- 方法体内部：用详细注释写清未来实现步骤

**Stub 注释模板：**

```java
/**
 * 创建订单
 *
 * 实现步骤：
 * 1. 标准化入参(校验非空、字段长度)
 * 2. 检查用户权限(当前用户是否有下单权限)
 * 3. 检查商品库存(调用 inventory-service)
 * 4. 计算订单金额(应用优惠券、运费规则)
 * 5. 持久化订单(写 orders + order_items)
 * 6. 扣减库存(异步消息或同步调用)
 * 7. 返回订单 ID
 */
@PostMapping("/api/v1/orders")
public OrderDTO createOrder(@RequestBody CreateOrderRequest req) {
    // 等待协同模式下实现具体逻辑
    return null;
}
```

**用户审批点（这是协同模式最关键的步骤）：**
- URL 命名
- 方法签名（参数、返回值类型）
- Controller 类名和文件位置
- 是否分组到不同 Controller
- 注释里的实现步骤是否符合预期

**用户经常在此步反复调整：**
- "这个接口应该叫 createOrder 而不是 addOrder"
- "返回值应该是 Result<OrderDTO> 而不是裸 OrderDTO"
- "文件应该放到 controller/order/ 而不是 controller/"

### 步骤 6：接口实现

**Agent 输出：** Service / Repository / 数据库访问等具体实现
- 业务逻辑代码
- 数据库访问（SQL 或 JPA）
- 异常处理

**用户审查：**
- 每一行业务逻辑都可能需要用户调整
- 用户会特别关注：业务规则实现、状态判断、金额计算
- 这是用户最仔细看的代码,要确保简洁、清晰、可读

**协同纪律：**
- 每完成一个 Service 方法,停下等用户审查
- 不要一次性提交多个 Service 实现
- 不要在 Service 里加用户没要求的辅助方法

### 步骤 7：前端开发

**Agent 输出：** 按顺序完成

1. **页面骨架：** 创建空页面组件,只放占位符
2. **路由配置：** 在路由表里注册新页面
3. **组件放置：** 按页面规划放置 UI 组件
4. **联调：** 调用后端接口,处理数据加载、错误、空状态

**用户审批点：**
- 页面命名和路由路径
- 组件拆分粒度
- 状态管理方案（useState / Redux / Zustand）
- API 调用层组织（是否统一到 request/）

**不允许：**
- Agent 自行选择 UI 组件库
- Agent 自行设计页面布局（信息层级）
- Agent 自行添加用户没要求的交互（动画、过渡）

## 协同模式的常见错误

- **跳过审批点直接往下做**——失去协同意义
- **每行代码都问**——太碎,失去节奏;按"步骤"审批,不要按"行"审批
- **用户暂时离开时自动继续**——协同模式必须等用户,不能擅自推进
- **忽视用户的命名/位置调整**——这些是用户对代码 ownership 的表达,必须尊重
- **在 stub 注释里写错实现步骤**——会让用户对实现产生错误预期,后续审查会反复修改
- **协同模式下还 spawn 多个子代理并行**——协同是用户逐步引导的过程,不适合并行

## 协同模式完成时

全部步骤完成后,自动进入 Phase 3: 验证。调用 `$ep-delivery-review` 做最终评审。

评审完成后,用户在交付决定上签字（Approved / Approved with follow-ups / Not approved）。

此时用户对每个文件、每个接口、每个命名都审查过——这就是协同模式的核心价值。
