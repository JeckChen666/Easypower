# 架构边界与演进模式

## 深模块

模块的外部接口应让调用者用较少知识获得完整业务能力。接口包括类型，也包括不变量、顺序、错误、配置和性能语义。

用三个问题检查：

- 删除该模块后，复杂度会消失还是散落回多个调用者？
- 业务规则变化能否集中修改和验证？
- 调用者和业务测试能否通过同一接口观察结果？

如果模块只是转发参数，删除后没有复杂度重新出现，它通常不值得存在。

## 依赖与 Adapter

| 依赖 | 处理方式 |
|---|---|
| 进程内计算 | 放入深模块，通过业务接口直接验证 |
| 有本地替代物的存储/运行时 | 在模块内部使用真实替代物，不暴露测试专用接口 |
| 自有远程系统 | 在网络接缝定义 Port，生产和内存 Adapter 分别实现 |
| 第三方系统 | 注入最小 Port，测试使用受控 Adapter |

一个实现通常不值得单独抽象。存在真实替换、独立失败或协议演进时，接缝才有收益。

## 计算与查询分流

区分业务计算、交互查询和大规模导出：它们可以共享版本化语义，但不必共享同一运行路径。性能优化必须证明结果等价，并基于真实查询分布、选择度、并发、扫描量和新鲜度验证。

## 版本化与可重建层

将不可变输入、业务版本和可重建服务层分开考虑。历史追溯至少能回答：使用了什么输入、什么业务口径和什么实现版本。缓存、索引或分析副本不应成为无法重建的唯一事实源。

## 渐进迁移

优先使用：建立新契约 -> 双写或影子运行 -> 差异验证 -> 按业务切片灰度读取 -> 观察 -> 停用旧路径。涉及 Schema 时采用 expand -> migrate -> contract，保持中间版本兼容。

每一步都声明：业务可见结果、进入条件、退出条件、回滚点和需要保持的核心业务证据。
