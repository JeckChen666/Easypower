# 评审范围与输入

## 固定范围

评审前记录：

```markdown
**业务切片/交付：**
**Spec：** <路径、版本、批准状态>
**Plan/子 Plan：** <路径>
**基线：** <commit、tag、产物版本或数据版本>
**当前：** <commit、工作区或产物版本>
**Diff/产物：** <命令或路径>
**证据：** <目录和关键条目>
**仓库规范/ADR：** <路径>
```

Git 评审优先比较共同祖先到当前版本，并记录实际提交列表。工作区未提交时同时检查暂存和未暂存差异。非代码交付使用等价的输入、目标产物和版本边界。

## 输入可信度

- Spec 必须是已批准版本，草案只能提供背景；
- Plan 说明预期范围，但不能覆盖 Spec；
- 实现摘要用于导航，不作为事实；
- 测试日志必须有命令、输入、环境和当前版本；
- 截图或导出文件应能关联到数据和构建版本；
- 性能证据需要固定负载和对照基线。

无法确定范围时先澄清，不把整个仓库或全部历史纳入评审。发现与当前交付无关的旧问题时仅在其会阻断本次业务结果或被本次改动放大时报告。

## 独立审查上下文

高风险或大范围交付可把两条轴交给独立只读上下文。每个审查者只接收范围、权威契约、真实 diff/产物和证据入口，不接收实现者的结论。协调 Agent 负责去重、核验和最终门禁；审查者不得修改代码、Plan 或证据。
