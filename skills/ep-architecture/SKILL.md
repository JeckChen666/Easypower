# 设计业务架构

## 不要进入本 Skill

- 普通实现选择（库选型、字段命名、局部重构）→ 留给执行 Agent
- 仅靠讨论或现有证据就能决定 → 返回 `ep-planning` 直接拍板
- 已有确定方案,只缺架构文档 → 写 ADR,不进入本 Skill
- 只是为了看起来专业而制造设计阶段 → 直接拒绝

## 入口检查

- [ ] 决定会影响 Spec 或多个业务切片
- [ ] 存在至少两个实质不同的系统方案
- [ ] 业务负载、不变量或迁移路径有可观察的区分维度
- [ ] 没有更好的入口（事实不清走 `$ep-research`,长期系统取舍走 `$ep-architecture`,状态/计算/交互不清走 `$ep-prototyping`）

## 输出契约

- 推荐方案 + 至少一个被否决的替代方案（同一决策矩阵比较）
- 业务负载模型（不只是单个性能数字）
- 业务契约、Schema、迁移、回滚约束回写到 Spec / 主 Plan
- 详细协议见 [decision-framework.md](references/decision-framework.md)、[architecture-patterns.md](references/architecture-patterns.md)

## 核心原则

架构服务于已知的业务场景、负载和不变量。先证明决定解决了什么业务问题，再比较系统级方案；不要从技术品牌、单一性能数字或抽象偏好反推需求。

本 Skill 只处理会影响 Spec（业务规格）或多个业务切片的重要决定。普通实现选择留给 Agent（执行代理）；没有重要架构未知项时返回上游流程，不制造额外设计阶段。

## 1. 建立事实边界

读取相关 Spec、主 Plan、代码、数据形态、运行证据和已有 ADR。明确当前要决定的一个问题，并区分：

- 已确认的业务事实与不变量；
- 当前系统和组织约束；
- 有证据的负载与故障模式；
- 尚未验证的假设；
- 必须由用户决定的业务取舍。

如果 Spec 未批准，可以协助形成候选方案，但不要把架构结论写成已批准契约。每次只向用户推进一个会改变方案选择的决定，并给出推荐。

## 2. 建立业务负载模型

读取 [decision-framework.md](references/decision-framework.md)。不要只定义“响应时间小于 N”。至少覆盖对方案有区分力的场景：输入规模与增长、查询或写入形态、并发与突发、数据新鲜度、正确性与一致性、权限隔离、故障恢复、变更频率和成本边界。

无法获得真实数据时使用明确标注的范围和假设。把取得测量结果作为决策验证项，不把猜测伪装成指标。

## 3. 设计至少两个可行方案

针对同一业务契约设计至少两个实质不同的系统方案，通常包含一个最小演进方案。横向检查：

- 业务计算在哪里发生，如何保证结果等价；
- 数据如何表示、版本化、查询和恢复；
- 用户交互和批处理如何分流；
- 公共接口隐藏什么复杂度，调用者必须知道什么；
- 一致性、失败语义、安全和可观测性；
- 如何双跑、灰度、迁移、回滚和退出旧路径。

设计模块时读取 [architecture-patterns.md](references/architecture-patterns.md)。优先小接口、深实现和变更局部性；只有确实存在生产实现和替代实现时才创建 Adapter（适配层），不要只为测试增加抽象层。

## 4. 比较并形成推荐

使用同一决策矩阵比较所有方案：业务适配度、正确性风险、负载余量、演进成本、运维复杂度、可逆性、接口深度、变更局部性和验证难度。

先给推荐，再说明它在什么假设下成立、代价是什么、什么证据会推翻它。不要在缺少关键负载或组织约束时直接锁定数据库、消息系统或部署拓扑。

自然语言无法可靠区分方案时，选择最小 Research（资料调研）、Prototype（原型验证）或基准实验。实验只回答当前决策问题，不顺便建设生产系统。

## 5. 取得批准并回写上游

分段与用户确认驱动因素、推荐方案和迁移策略。批准后：

- 将业务可见的质量属性、不变量和关键架构决定回写 Spec；
- 将迁移顺序、契约冻结、验证和回滚约束回写主 Plan；
- 只有跨功能、难以逆转且项目已有约定时才新增 ADR；
- 记录被否决方案及否决原因，但不复制完整讨论。

返回 `ep-planning` 继续规划，或返回 `ep-execution` 继续已批准切片。架构 Skill 不直接接管长期实现。

## 完成条件

- 推荐方案对应明确的业务场景和负载，而非抽象最佳实践；
- 至少一个可行替代方案经过同维度比较；
- 核心业务闭环的正确性证据在迁移前后保持成立；
- 公共接口、Schema、一致性和失败语义明确；
- 迁移、双跑、回滚和观测入口可执行；
- 重要假设有验证方法和触发重新决策的条件；
- 用户批准会改变业务契约或关键架构的决定。

需要完整 BI 示例时读取 [bi-architecture-example.md](references/bi-architecture-example.md)。

## 常见错误

- 先选技术产品，再补业务理由。
- 用单个峰值、行数或延迟指标代替负载模型。
- 只优化计算，不检查查询、存储、网络和用户工作流。
- 只给一个精致方案，让用户无法比较取舍。
- 在方案阶段写大量生产代码或提前完成所有迁移细节。
- 为每个依赖创建接口和 Mock，增加浅层抽象。
- 迁移方案没有业务等价验证、双跑或回滚路径。
