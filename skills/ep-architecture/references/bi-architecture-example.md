# BI 报表架构决策示例

## 决策问题

现有流程读取 Excel、集中计算并返回完整 JSON。数据增长后需要交互筛选、历史查询和重新计算。Excel 目标结果仍是业务正确性的依据。

先确认三个业务场景：标准报表生成、用户交互查询、全量导出/历史重放。分别记录规模、频率、并发、新鲜度、容差、权限和恢复要求。

## 可行方案

### A：最小演进

保留现有计算语义，将输入和结果版本化；结果改为分区文件或结构化表，API 使用分页和受限排序。适合增长可控、查询组合有限、团队不希望增加新基础设施的情况。

### B：对象存储加查询服务层

不可变输入和列式产物保存在对象存储，关系库存运行、版本、血缘和权限元数据；服务层按真实查询负载选择现有数据库或分析引擎。适合历史重放、较大数据量和多种读取路径。

### C：独立分析服务层

对象存储保存可重放事实，专用列式引擎承载交互聚合，关系库管理控制面。适合高并发、多维过滤和持续增长已经由遥测证明的情况，但增加同步、运维和成本复杂度。

不要在确认查询矩阵、现有平台能力和运维边界前直接选择具体产品。

## 推荐结构

如果负载证明确需分析服务层，推荐将原始输入、业务计算、版本发布、交互查询和导出分成可独立演进的模块。用户查询只访问已发布版本；新版本通过 Excel Golden Sample（基准样本）、分组总量和边界数据差异验证后原子发布，失败时旧版本继续服务。

性能验收要按常见查询、探索查询和导出分别设置预算，并测量并发、选择度、扫描量、聚合基数、权限成本和数据新鲜度。单独写“亿级数据两秒返回”无法指导架构选择。

## 回写

Spec 记录业务场景、结果容差、版本语义、权限和可用性。主 Plan 记录基准结果、新链路影子运行、差异检查、灰度查询、回滚观察和旧链路退出。只有基准数据和组织约束足够明确时，具体产品选择才进入批准范围。
