# 业务架构决策框架

## 驱动因素

只收集会改变方案选择的事实。按业务场景建立负载矩阵，而不是列出一组孤立指标：

| 场景 | 输入与增长 | 读写/计算形态 | 并发与时效 | 正确性/一致性 | 失败与恢复 | 成本边界 |
|---|---|---|---|---|---|---|
| 核心闭环 | ... | ... | ... | ... | ... | ... |
| 常见交互 | ... | ... | ... | ... | ... | ... |
| 峰值/批处理 | ... | ... | ... | ... | ... | ... |
| 历史重放 | ... | ... | ... | ... | ... | ... |

再补充组织现实：现有技术栈、团队能力、托管服务、合规、部署环境、交付期限和可接受的运维负担。

## 方案最低内容

每个方案说明：

1. 端到端数据流和控制流；
2. 核心模块及其外部接口；
3. 计算、存储、查询和缓存职责；
4. 版本、一致性、权限和失败语义；
5. 对现有核心业务证据的复用方式；
6. 渐进迁移、回滚和可观测性；
7. 容量与成本如何随真实负载变化。

不要让“维持现状”成为虚假的陪衬。如果现状无法满足硬约束，最小演进方案应说明最少改变哪些部分才可行。

## 决策验证

优先使用最便宜且能推翻错误方案的证据：

- 代码与生产遥测回答现状问题；
- 官方资料回答产品能力或限制；
- 小型原型回答接口、交互或可行性；
- 固定数据与环境的基准回答容量问题；
- 双跑和差异报告回答业务等价问题；
- 故障注入或恢复演练回答一致性和恢复问题。

验证没有通过前，将结论标为“条件推荐”，不要伪装成已批准事实。
