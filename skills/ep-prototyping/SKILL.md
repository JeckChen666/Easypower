# 用原型验证决策

## 不要进入本 Skill

- 问题可以用文档、官方资料或现有证据回答 → 走 `$ep-research`
- 问题是长期系统取舍（数据库/中间件/部署拓扑）→ 走 `$ep-architecture`
- 已有明确决策,只是要"做个样子" → 直接拒绝
- 一次性生产实现 → 不叫原型,叫产品

## 入口检查

- [ ] 必须运行、操作或观看后才能判断
- [ ] 有清晰的判定标准（什么观察能区分候选答案）
- [ ] 能用一次性代码 / 一次性页面回答
- [ ] 没有更好的入口（外部事实走 `$ep-research`,长期架构走 `$ep-architecture`,业务术语歧义走 `$ep-domain-modeling`）

## 输出契约

- 决策问题 + 候选答案 + 判定标准
- 可运行的最小验证产物（一条命令或一个 URL）
- 观察记录 + 推荐 + 用户决定
- 决定回写 Spec,原型代码标记清理方式
- 详细协议见 [logic-prototype.md](references/logic-prototype.md)、[ui-prototype.md](references/ui-prototype.md)、[technical-spike.md](references/technical-spike.md)

## 核心原则

Prototype（原型）是为了回答一个决策问题而制作的一次性验证产物，不是生产实现的早期版本。问题决定原型形态；取得足够证据后停止，把结论回写业务契约，并清理未被选择的实现。

## 1. 确认原型是正确工具

先写出唯一决策问题、候选答案和什么观察会区分它们：

```markdown
**决策问题：**
**候选答案：**
**必须观察的场景：**
**判定标准：**
**不回答：**
**停止条件：**
```

如果问题依赖官方能力、法规或外部事实，明确调用 `$ep-research`；在用户更新中写出 Skill 名称，不要只说“先查资料”。如果问题是长期系统取舍，明确调用 `$ep-architecture`。只有必须运行、操作或观看后才能判断时才制作原型。

## 2. 选择最小原型

- 业务逻辑、公式、状态转换或数据形状：读取 [logic-prototype.md](references/logic-prototype.md)；
- 页面布局、信息层级或交互流程：读取 [ui-prototype.md](references/ui-prototype.md)；
- 文档无法回答的技术可行性或外部集成行为：读取 [technical-spike.md](references/technical-spike.md)。

一个原型只选择一个主要分支。不要把 UI、后端、数据库和完整集成一起建设来回答一个局部问题。

## 3. 明确隔离方式和生命周期

复用项目已有语言、运行时、组件和任务工具，不为原型引入新的框架或基础设施。原型使用内存、固定样本、Stub（桩实现）、Sandbox（隔离测试环境）或只读数据；除非决策问题本身涉及持久化，不接生产写路径。

将代码标记为 `PROTOTYPE`，放在方便清理的独立位置或临时分支。需要嵌入现有页面时使用明确的原型开关或原型路由，并保证生产构建不可访问。创建前记录清理方式，不让实验代码变成无人负责的正式模块。

## 4. 构建可观察的验证产物

只实现让判定标准可观察的路径：

- 每次操作展示相关输入、状态、输出和差异；
- 所有候选方案使用同一组业务场景和数据；
- 一条命令或一个明确 URL 即可运行；
- 省略生产级持久化、权限、错误处理、抽象、监控和全面测试；
- 只有缺少它会使决策证据不可信时才补最小保护。

原型至少实际运行一次，证明产物可用且能区分候选答案。不要因为“只是原型”交付空壳或无法启动的页面。

## 5. 组织用户判断

先让用户完成相同的关键任务或查看相同场景，再比较：哪些业务不变量成立、哪些状态令人意外、哪个方案更符合高频工作、代价和边界是什么。

Agent（智能体）可以根据观察给出推荐，但业务口径和产品取舍由用户批准。发现问题定义错误时先更新决策问题，不继续给错误原型加功能。

## 6. 记录结论并清理

保存简短结果：问题、使用的场景、观察、被否决选项、推荐、用户决定和仍未知事项。将决定回写 Spec（业务规格）的规则、验收、质量属性或决策依据；影响计划时更新对应切片约束。

默认删除原型壳、切换器、Stub 和未选方案。只有用户明确要求保留原始实验时，才放入不会被发布的临时分支或项目约定位置，并留下到结论的链接。被选中的逻辑或 UI 仍按生产标准重新实现和验证，不直接复制未经工程化的原型。

## 完成条件

- 一个明确问题和判定标准；
- 验证产物实际可运行，并能展示相关状态或交互；
- 候选答案使用同一业务场景比较；
- 观察足以支持推荐或明确仍缺什么；
- 用户批准业务或产品决定；
- 决定已回写权威文档，原型已有清理或隔离结果。

## 常见错误

- 用原型代替可以查证的官方事实。
- 同时回答多个问题，逐步长成半套生产系统。
- 为一次性代码补完整测试、抽象、权限和部署流水线。
- UI 方案只换颜色，不改变信息层级或工作流。
- 在空白页面评审本应嵌入现有产品的交互。
- 把胜出的原型代码未经重写和验证直接上线。
- 保留所有实验分支、路由和切换器污染主线。
