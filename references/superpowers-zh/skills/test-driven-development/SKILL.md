# 测试驱动开发（TDD）

通过 RED-GREEN-REFACTOR 循环实现行为：先写测试，亲眼确认测试失败，再写最小实现，确认通过后才重构。

**核心原则：没有观察到测试失败，就不能确认测试真正验证了目标行为。**

## 铁律

```text
没有失败测试，就不要写生产代码。
```

## RED-GREEN-REFACTOR

### RED：先写一个失败测试

1. 从用户可观察的行为开始，而不是从内部函数开始。
2. 为一个行为写一个最小测试。
3. 运行测试，确认它因为缺少目标行为而失败。
4. 检查失败原因：不能是语法错误、导入错误、测试配置错误或断言写错。

测试没有失败时，先修正测试或选择尚未实现的行为；不要直接进入实现。

### GREEN：最小实现

只写让当前失败测试通过的代码。不要提前添加未来功能、通用抽象、额外配置或未经测试的优化。运行测试并确认通过；若失败，先修实现，再运行完整的相关测试。

### REFACTOR：保持绿色后改进

测试通过后再清理重复、命名、结构和复杂度。每次只做一种重构，并在每一步后运行测试。重构不能改变行为或扩大范围。

## 测试边界

优先测试公共接口和真实用户流程。测试应说明“输入什么、观察到什么、为何重要”，避免紧耦合到私有方法、调用次数和内部变量。每个测试只验证一个行为，失败信息应能直接指出问题。

## 隔离依赖

只有在依赖不可控、昂贵、非确定或有副作用时才使用 mock/stub。不要 mock 自己不理解的接口，也不要为了让单元测试通过而编造不完整的 mock。对于组件之间的契约和关键集成路径，保留真实集成测试。

详细反模式见 [testing-anti-patterns.md](testing-anti-patterns.md)。

## 常见合理化借口

- “改动太小，不需要测试”：小改动同样可能改变边界行为。
- “我先写代码，之后补测试”：事后测试容易只验证当前实现。
- “测试很难写”：通常说明接口或边界需要重新设计。
- “先把测试调绿”：不明原因的绿色没有证据价值。
- “只加一个超时”：先判断是否应等待明确事件。

## 完成标准

实现完成前确认：

1. 每个重要行为都有测试。
2. 每个新测试都曾明确失败过。
3. 生产代码只包含测试要求的行为。
4. 相关单测、集成测试和完整回归测试均通过。
5. 测试稳定、隔离，并且失败时能帮助定位根因。
