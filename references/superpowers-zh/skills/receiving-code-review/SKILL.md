# 接收代码评审

代码评审需要技术判断，不需要情绪化回应。

**核心原则：先验证再实现；先询问再假设；技术正确性高于社交上的顺从。**

## 标准响应顺序

收到评审意见后依次执行：

1. **完整阅读**：先看完全部意见，不立即反应。
2. **理解**：用自己的话重述要求；不清楚就询问。
3. **验证**：对照实际代码、测试、调用方和运行环境。
4. **评估**：判断建议是否适合当前代码库，是否会破坏已有行为。
5. **回应**：给出技术确认或基于证据的异议。
6. **实现**：一次处理一项，并逐项测试。

## 禁止的回应

不得在验证前说“你完全正确”“好建议”“我马上实现”。改为重述技术要求、提出澄清问题，或者直接开始检查。

## 含糊意见

有任何一项不清楚时，先暂停全部实现，集中询问所有不明确的地方。部分理解会导致部分实现，最终容易得到错误方案。不要先改清楚的项目、把疑问留到最后。

## 外部评审的核验

实现外部意见前检查：

1. 对当前代码库是否技术正确。
2. 是否会破坏现有功能、兼容性或平台支持。
3. 当前实现为何这样设计，是否有历史约束。
4. 是否真的有调用方或用户需求。
5. 评审者是否掌握完整上下文。

无法快速验证时，明确说明缺少什么证据，并询问是继续调查还是等待补充信息。若意见与用户已经确认的架构决策冲突，先和用户讨论。

## YAGNI 检查

评审者提出“更专业”的新接口、指标、筛选、导出或数据库功能时，先在仓库中查找真实调用。没有调用方就指出它目前未被使用并询问是否删除；有实际使用再按需求实现。不要因为看起来专业而增加未被要求的功能。

## 实现顺序

多项意见按以下顺序处理：

1. 先澄清全部疑问。
2. 先修复阻塞、安全和正确性问题。
3. 再处理简单的拼写、导入和局部修复。
4. 最后处理重构和复杂逻辑。
5. 每项单独测试，最后运行回归验证。

## 适合提出异议的情况

建议会破坏功能、缺少上下文、违反 YAGNI、与技术栈不匹配、涉及兼容性、或与用户的架构决定冲突时，应基于代码、测试和具体风险提出异议，而不是为了避免不舒服而照改。

若后来验证发现自己判断错误，简短说明“已核实，你的判断正确，原因是……”，然后修复，不要长篇辩解或道歉。

## GitHub 讨论串

回复 GitHub 行级评审时，使用评论线程回复接口，例如：

```bash
gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies
```

不要把行级意见另发成顶层 PR 评论。

## 底线

外部评审是需要评估的建议，不是无需思考的命令。核验、质疑，然后实现；让代码和测试表达你已经处理了意见。
