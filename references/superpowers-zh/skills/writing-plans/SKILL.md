# 编写实现计划

把已确认的需求转换成另一位不了解项目上下文的工程师也能执行的计划。计划必须具体到文件、代码边界、测试和验证命令。

## 开始前

1. 阅读设计文档、需求和相关 skill。
2. 检查仓库结构、现有实现、测试、配置和近期提交。
3. 确认基线测试状态。
4. 找出依赖、共享状态、风险和需要用户决定的事项。

不要在需求仍含糊或设计未批准时写实现计划；先回到 `brainstorming`。

## 计划结构

计划保存到 `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`，包括：

- 目标和非目标；
- 当前实现和相关文件；
- 任务顺序及依赖；
- 每项任务的文件路径、符号或代码区域；
- 实现逻辑、边界条件和错误处理；
- 测试先行步骤、测试命令和预期结果；
- 完成定义及最终验证。

## 任务粒度

每项任务应能在约 2-5 分钟内理解和开始执行，且只包含一个清晰目标。任务模板：

```markdown
### 任务 N：<动词开头的目标>

**文件：** `path/to/file.ts:SymbolName`
**依赖：** 任务 <N-1>（如有）

**步骤：**
1. 先添加描述目标行为的失败测试。
2. 运行 `<命令>`，确认因预期原因失败。
3. 在 `<位置>` 实现最小行为。
4. 运行 `<命令>`，确认测试通过。
5. 检查 diff，确认没有计划外修改。

**验收：** <可观察、可验证的结果>
```

避免只写“实现功能”“更新测试”这种无法执行的任务；避免把多个无关模块塞进一项任务。

## 设计约束

- 遵循现有项目的命名、模块、错误处理和测试约定。
- 明确新增或修改的接口，以及所有调用方。
- 说明迁移、兼容性、回滚和资源清理策略。
- 使用 YAGNI，删除没有验收依据的扩展功能。
- 使用 TDD：每个行为先写测试并观察失败。
- 任务之间有共享文件或状态时，明确顺序，不能假设并行安全。

## 审阅计划

写完后从零上下文重新阅读，检查路径是否真实存在、任务是否覆盖全部需求、顺序是否可执行、验证命令是否足够、是否有未处理的失败路径。必要时使用 `plan-document-reviewer-prompt.md` 做独立审阅。

计划须经用户批准后才能执行。执行时选择 `subagent-driven-development` 或 `executing-plans`，不要直接跳过计划进入编码。
