# 完成前验证

没有运行验证就声称完成是不可靠的。完成、修复、通过等结论都必须由当前运行的命令支持。

## 铁律

```text
没有新鲜的验证输出，就不能声称结果成功。
```

## 验证门

在最终回复、提交或创建 PR 前：

1. 选择能直接证明目标行为的命令，而不是只运行相关但不充分的命令。
2. 执行命令并等待结束。
3. 阅读完整输出，确认退出码、失败数、警告和生成物。
4. 将结果与用户需求逐项对照。
5. 验证失败时报告失败，不要包装成“基本完成”。

示例：

```bash
npm test
npm run build
git diff --check
git status --short
```

按项目实际工具替换命令；不要盲目运行不适用的命令。

## 常见不足

- “代码看起来正确”不是运行证据。
- 只运行单测不能证明构建、集成或用户流程正确。
- 上一轮输出不能证明本轮修改仍正确。
- 进程仍在运行、输出被截断或命令被中断，都不能视为通过。
- 只检查退出码而不阅读输出，可能遗漏失败测试或警告。

## 红旗：停止并重新验证

当你准备说“应该可以”“没必要再测”“改动太小”“测试之前已经跑过”时，先停下来运行验证。不要通过修改断言、跳过测试、增加任意重试或隐藏日志来制造绿色结果。

## 最终报告

报告实际运行的命令和关键结果，例如：

```text
验证：npm test（通过，42 tests）
验证：npm run build（通过）
验证：git diff --check（通过）
```

若某项无法运行，明确说明原因、未验证的风险和建议的下一步；不要声称全部完成。
