# 并行调度代理

将独立问题交给拥有隔离上下文的专门代理并行处理。每个代理只接收完成自身任务所需的信息，不继承当前会话的历史；主代理负责协调、审查和整合。

**核心原则：一个独立问题域对应一个代理，同时调度可以并行的代理。**

## 适用场景

- 3 个或更多测试文件失败，且根因不同。
- 多个子系统各自独立损坏。
- 每个问题无需了解其他问题即可分析。
- 调查之间没有共享状态。

## 不适用场景

- 失败可能由同一个根因引起。
- 必须先了解完整系统状态。
- 仍处于探索阶段，不知道问题边界。
- 代理会编辑相同文件、占用相同资源或互相干扰。

## 标准流程

### 1. 识别独立问题域

按故障的代码边界分组，例如：工具审批、批处理完成、取消行为。修复一个分组不应改变另一个分组的行为。

### 2. 编写聚焦的任务

每个代理的任务应包含：

- 明确范围：一个测试文件或一个子系统。
- 清晰目标：要修复什么或要回答什么。
- 约束：允许及禁止修改哪些内容。
- 输出格式：根因、修改和验证结果。

### 3. 同一轮发出并行调度

在同一条消息中发出多个代理调用，它们才会并行运行：

```text
Subagent (general-purpose): "修复 agent-tool-abort.test.ts 的失败"
Subagent (general-purpose): "修复 batch-completion-behavior.test.ts 的失败"
Subagent (general-purpose): "修复 tool-approval-race-conditions.test.ts 的失败"
# 三个任务同时运行。
```

一个回复发一个代理会变成顺序执行。

### 4. 审查并整合

代理返回后，逐个阅读摘要，检查修改冲突，运行完整测试套件，并抽查代理是否引入了系统性错误。

## 代理提示词模板

提示词要聚焦、自包含，并明确输出：

```markdown
修复 `src/agents/agent-tool-abort.test.ts` 中的 3 个失败测试：

1. “should abort tool with partial output capture” 期望消息包含 `interrupted at`
2. “should handle mixed completed and aborted tools” 中快速工具被错误取消
3. “should properly track pendingToolCount” 期望 3 个结果但得到 0 个

这些问题可能与时序或竞态有关。请：
1. 阅读测试并说明每个测试验证的行为。
2. 区分时序问题和产品代码缺陷，找到根因。
3. 使用基于事件的等待替换任意超时；仅在确认是实现缺陷时修改生产代码。
4. 不要只是增加超时时间。

返回：根因、修改内容、运行过的验证命令及结果。
```

避免“修复所有测试”这种过宽请求；不要省略错误信息、测试名称和文件边界；也不要允许代理随意重构整个项目。

## 整合检查

代理完成后：

1. 阅读每个摘要，并对照实际 diff。
2. 检查是否编辑同一文件或共享资源。
3. 运行完整测试套件，而不只运行各自的局部测试。
4. 对关键路径抽查边界情况和错误处理。

并行化的收益来自独立性，不是把相关工作强行拆开。只要任务之间有因果关系或共享状态，就回到统一调查或顺序执行。
