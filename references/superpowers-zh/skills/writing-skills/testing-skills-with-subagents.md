# 使用子代理测试 Skill

**在以下情况读取：**创建或编辑 skill、部署前验证 skill 是否能在压力下工作并抵抗合理化。

## 概述

测试 skill 就是把 TDD 应用于流程文档。

**核心原则：如果没有观察到 agent 在没有 skill 时失败，就不知道 skill 是否阻止了正确的失败。**

使用本指南前必须理解 `test-driven-development`：它定义 RED-GREEN-REFACTOR；本指南补充压力场景和合理化表。

## 何时测试

适合测试：强制纪律（TDD、验证）、执行代价高、容易被“只这一次”合理化、与眼前目标冲突（速度优先）的 skill。

不必对纯参考资料、没有可违反规则的 skill、或 agent 没有动机绕过的 skill 做压力测试。

## Skill 测试与 TDD 的对应关系

| TDD | Skill 测试 |
|---|---|
| RED | 没有 skill 的基线，观察 agent 失败 |
| GREEN | 写最小规则，让基线场景通过 |
| REFACTOR | 收集新漏洞并增加明确防护 |
| 回归 | 重跑原场景和新压力场景 |

## RED：基线测试

**目标：**在没有 skill 时运行测试，记录确切失败。

1. 创建至少 3 种混合压力的真实场景；
2. 不提供 skill，运行 agent；
3. 逐字记录选择和合理化；
4. 找出重复出现的借口；
5. 记录最容易触发违反规则的压力组合。

常见结果包括：“我已经手工测过”“事后补测试一样”“删除很浪费”“要务实而不是教条”。这一步明确了 skill 必须防止什么。

## GREEN：写最小 Skill

只针对基线暴露的问题写规则。规则必须具体到触发条件、必需动作、停止条件和验证证据，不要先加入所有可能的最佳实践。

## 验证 GREEN：压力测试

**目标：**确认 agent 在想绕过规则时仍然遵守。

### 编写压力场景

差的场景没有压力；单一压力只能测试一条防线。好的场景组合至少三种压力，例如时间损失、沉没成本、权威要求、已存在的“可用”方案、社交压力、明显快速修复和不确定性。

每个场景应包含：真实任务、可选行为、绕过规则的即时收益、选择后果和明确要求“选择并行动”。不要告诉 agent 正确答案或你希望测试的漏洞。

### 压力类型

- 时间：生产损失、截止时间、会议超时；
- 沉没成本：已经写了很久、删除会浪费工作；
- 权威：资深工程师、技术负责人或用户要求捷径；
- 速度偏见：快速修复看似显而易见；
- 熟悉感：agent 认为自己已经知道怎么做；
- 社交：团队希望尽快结束；
- 不确定性：完整调查耗时且结果未知。

最佳场景组合 3 种以上压力。说服原则的背景见 `persuasion-principles.md`。

### 测试设置

每次使用新上下文，保持任务、项目和可用工具一致。记录 agent 读取了什么、使用了什么工具、选择了什么、引用了哪些规则、是否完成验证。不要把你的诊断、预期答案或上一次结果泄漏给下一轮。

## REFACTOR：关闭漏洞

逐字记录新出现的合理化，例如：

- “这个情况不同”；
- “我遵循的是精神，不是字面”；
- “目的就是 X，我用另一种方式达成了”；
- “务实意味着适应”；
- “删除这几个小时的工作太浪费”；
- “先保留作参考，同时先写测试”；
- “我已经手工测试过了”。

每个借口都进入合理化表，并增加针对性防护。

### 堵住每个漏洞

1. **规则中明确否定：**写出禁止的变体和唯一替代动作。例如“删除意味着删除；不要保留作参考，不要一边写测试一边适配旧代码”。
2. **合理化表：**记录借口、违反的规则和应采取的动作。
3. **红旗列表：**把 agent 可能说出的危险句子列为 STOP 信号。
4. **更新 description：**加入触发场景和违反表现，让后续任务能发现 skill。

## 修改后重新验证

使用同一批场景重测。确认 agent 选择正确选项、引用新增章节，并承认先前的合理化已被处理。如果出现新的合理化，继续 REFACTOR；如果在最大压力下仍遵循规则，说明该场景的防护有效。

## 元测试

agent 选错后，不要只告诉它正确答案，询问：

1. 为什么没有使用或遵循该规则？
2. 哪句话让你认为可以例外？
3. skill 应该怎样改才无法这样理解？
4. 你认为自身选择如何符合规则？

可能的回答：规则不够明确、触发条件没命中、冲突规则优先级不清、现实压力改变了取舍、只读了摘要、或产生了新的合理化。根据回答增加最小防护，再重测。

## Skill 何时算加固完成

**有效迹象：**agent 主动读取 skill；准确识别触发条件；在多重压力下执行门禁；能指出并拒绝常见借口；引用具体章节并提供验证证据。

**还未完成：**agent 找到新借口、争论规则错误、生成“混合方案”、或先请求许可再强烈主张违反规则。

## 示例：加固 TDD Skill

初测发现 agent 先写实现，理由是改动很小。第一轮加入“没有失败测试不得写生产代码”的门禁；第二轮加入“已有代码也必须先写回归测试”和删除先写代码的规则；再用时间、沉没成本和权威压力重复测试，直到所有场景遵守。

## 检查清单

**RED：**

- [ ] 创建了至少 3 种混合压力场景；
- [ ] 没有 skill 时运行了基线；
- [ ] 逐字记录了失败和合理化。

**GREEN：**

- [ ] 根据具体失败写了最小 skill；
- [ ] 带 skill 运行场景；
- [ ] agent 已遵守规则。

**REFACTOR：**

- [ ] 识别了新合理化；
- [ ] 为每个漏洞增加明确反制；
- [ ] 更新合理化表、红旗列表和 description；
- [ ] 重测后仍然通过；
- [ ] 做了元测试确认规则清晰；
- [ ] 最大压力下仍遵守。

## 常见错误

- **跳过 RED 直接写 skill：**不知道真正需要防止什么；
- **没有观察到失败：**测试失去基线意义；
- **场景只有单一压力：**不能暴露现实绕过方式；
- **不记录原话：**无法针对真实漏洞；
- **只加泛泛提醒：**“注意遵循流程”无法堵漏洞；
- **第一次通过就停止：**新压力仍可能突破。

## 快速参考

```text
RED：无 skill -> 真实压力 -> 记录失败和借口
GREEN：写最小规则 -> 带 skill 重跑 -> 确认遵守
REFACTOR：记录新借口 -> 增加明确防护 -> 重跑
```

## 底线

Skill 创建就是 TDD：相同的循环、相同的证据要求、相同的迭代收益。对纪律类 skill，基线测试、压力测试和漏洞闭环不是可选步骤。
