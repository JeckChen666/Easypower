# 编写 Skill

把 skill 当作“面向 agent 的可执行流程文档”。它不是博客、README 或泛泛的最佳实践，而是在特定请求触发后能指导另一个 agent 完成工作的最小上下文包。

**核心原则：用测试驱动流程文档，用实际任务验证行为。**

## Skill 的结构

每个 skill 至少包含一个 `SKILL.md`：

```text
skill-name/
├── SKILL.md
├── agents/openai.yaml       # 可选：界面元数据
├── scripts/                 # 可选：需确定性执行的脚本
├── references/              # 可选：按需读取的详细资料
└── assets/                  # 可选：输出时使用的资源
```

不要添加 README、安装指南、速查表、变更日志等与 agent 执行无关的文件。

## 触发元数据

frontmatter 只写 `name` 和 `description`。`name` 使用小写字母、数字和连字符，目录名必须与它一致。`description` 是唯一的主要触发入口，必须说明 skill 做什么以及何时使用；不要把完整工作流塞进 description。

```yaml
---
name: example-skill
description: 当出现具体问题、文件类型或工作流上下文时使用；说明本 skill 解决什么问题
---
```

描述应具体、可检索，并包含用户可能使用的同义表达。正文中的“何时使用”不能替代 frontmatter 中的触发条件。

## 渐进披露

按三层组织上下文：

1. 元数据：始终加载，保持简洁。
2. `SKILL.md` 正文：触发后加载，保留核心流程，通常少于 500 行。
3. `references/`、脚本和资源：只有任务需要时才读取或执行。

详细 schema、平台差异、示例和反模式放入一层深度的 references，并在正文中明确链接及读取条件。不要复制同一规则到多个文件。

## 编写流程

### 1. 先理解真实任务

收集 2-3 个具体使用例子：用户会怎么提问、需要什么输出、哪些错误最昂贵、哪些步骤不能省略。明确触发条件、边界和成功标准。若用户还没决定 skill 放在哪里，询问位置；已有 skill 则直接审阅现有结构。

### 2. 识别可复用资源

分析任务从零执行的过程，决定是否需要：

- `scripts/`：重复编写或容易出错、需要确定性的操作；
- `references/`：schema、平台映射、详细规范和长示例；
- `assets/`：会被最终输出使用的模板、图标、字体或样例。

脚本加入后必须实际运行测试。不要仅为“看起来完整”创建目录或文件。

### 3. 先写失败测试

为 skill 设计行为测试，而不是只检查 Markdown 是否存在。先用尚未完善的 skill 执行真实请求，记录 agent 是否跳过关键门禁、触发错误、输出格式不符或执行了危险动作。测试失败后再修改 skill。

### 4. 写最小核心流程

正文使用祈使式或不定式表达。每条规则应回答“在什么情况下做什么、如何判断完成、失败时怎么办”。高风险、脆弱的流程给出明确命令和停止条件；开放性强的工作只提供原则和决策点。

### 5. 用现实任务前向验证

完成后使用新上下文把 skill 放到类似用户请求中测试。评估触发、顺序、工具调用、输出质量和失败处理。验证时传递原始文件和任务，不要传递你的诊断或预期答案，避免测试被提示词泄漏影响。

## SKILL.md 推荐内容

```markdown
---
name: <name>
description: <触发条件和能力>
---

# <名称>

<一句话核心原则>

## 适用场景
<只补充触发后需要理解的边界>

## 流程
<按顺序的可执行步骤>

## 验证
<命令、证据和完成标准>

## 参考
- 需要平台或规范细节时，读取当前 skill 目录下与任务直接相关的 `references/` 文件。
```

标题可按 skill 类型调整。不要为了形式填充没有行动价值的段落。

## 设计防护栏

明确写出以下内容，尤其是曾在测试中失败的规则：

- HARD-GATE：什么条件满足前禁止继续。
- STOP：遇到哪些情况必须停下并询问。
- 最小变更和范围边界。
- 必须验证的命令和可接受输出。
- 用户确认、危险删除、外部系统写入等不可逆动作的确认方式。

规则要正向、具体，并解释“为什么”只在能防止错误判断时使用。不要依赖“应该”“尽量”“通常”这种无法判断的措辞。

## 反模式

- 触发描述过于宽泛，如“用于编码”。
- 把完整文档塞进 description，导致触发不稳定。
- 正文超过 500 行却没有拆 references。
- 只描述理念，不给步骤、工具、输出和停止条件。
- 只测试静态格式，没有验证 agent 是否遵守流程。
- 用过多否定规则堆砌防护，却没有明确替代动作。
- 包含与执行无关的 README、历史记录或作者说明。
- 通过示例泄漏评测的期望答案。

## 验证方法

### 流程型 skill

使用代表性任务，检查 agent 是否按顺序执行、是否在门禁处停止、是否正确处理异常和用户确认。

### 参考型 skill

给出需要查 schema、平台 API 或规范的任务，检查 agent 是否在需要时读取正确 reference，且没有把不相关资料全部加载进上下文。

### 脚本型 skill

实际运行脚本，覆盖成功、错误输入、边界值和重复执行；检查退出码、输出和副作用。

### 组合型 skill

验证端到端产物、工具调用顺序、测试结果和文件变更。复杂 skill 在重大修改后应进行至少一次独立前向测试；只有平台确实支持新子代理时才使用子代理。

## 迭代循环

```text
写一个最小规则
  -> 用真实任务测试
  -> 记录原始输出和失败点
  -> 修改 skill 或资源
  -> 再测同类任务和边界任务
  -> 运行静态校验
```

每次修改只解决已经观察到的问题，避免一次加入大量未经验证的规则。删除过时文件和占位示例，保持 skill 目录可发现、可维护。

## 完成清单

- [ ] `SKILL.md` 存在，frontmatter 只有 `name` 和 `description`。
- [ ] 名称、目录和触发描述符合命名规则。
- [ ] description 包含完整触发条件，而正文保持行动导向。
- [ ] 核心正文少于 500 行，长资料已拆分并直接链接。
- [ ] 所有引用路径真实存在。
- [ ] 脚本已实际运行并验证副作用。
- [ ] 已使用代表性任务进行前向测试。
- [ ] 已验证门禁、停止条件、用户确认和错误路径。
- [ ] 已运行 `quick_validate.py` 或等价静态校验。

## Skill 仓库的本地适配

不同 agent 平台的子代理、任务列表、浏览器和工作区能力不同。把平台差异放入 `references/`，在正文中先检测能力再选择路径。不要把某个平台的工具名伪装成所有平台都可用；当能力不存在时明确降级或停止。

把用户的本地偏好、中文术语和仓库约定写进 skill 的核心流程，但不要复制通用模型已经知道的常识。每一段内容都应能降低一次真实任务的错误率或减少重复探索。
