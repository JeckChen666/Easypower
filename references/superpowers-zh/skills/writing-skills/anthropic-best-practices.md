# Skill 编写最佳实践

本资料说明如何编写能被 agent 发现、正确读取并稳定使用的 skill。好的 skill 简洁、有结构，并通过真实任务测试。

## 核心原则

### 保持简洁

上下文窗口是共享资源。Skill 与系统提示词、会话历史、其他 skill 元数据和用户请求竞争上下文。启动时通常只加载所有 skill 的名称和描述；触发后才读取 `SKILL.md`，任务需要时才读取其他文件。因此正文仍应只保留 agent 不知道且确实需要的内容。

逐段询问：

- agent 真的需要这段解释吗？
- 这是否属于常识，可以省略？
- 这段内容是否值得占用 token？

好的示例只给出库名和最小代码；坏的示例会解释 PDF 是什么、库是什么以及一长段安装背景。默认 agent 足够聪明，只补充非显然的上下文。

### 设置合适的自由度

自由度应匹配任务的脆弱性和变化性：

- **高自由度：**多个方案都有效、决策依赖上下文、需要启发式判断时，使用原则和决策点。
- **中自由度：**存在推荐模式但允许变体、配置影响行为时，使用伪代码或带参数脚本。
- **低自由度：**操作脆弱、错误代价高或顺序不可变时，给出精确命令、参数和停止条件。

把 agent 想成沿路探索：没有危险的开阔地只需方向；两侧有悬崖的窄桥必须提供护栏和唯一安全顺序。

### 用计划使用的所有模型测试

Skill 是模型之上的附加指导，应使用计划支持的每个模型测试。快速模型可能需要更明确的步骤，强推理模型则可能被过度解释拖慢。目标是找到所有计划模型都能执行的最小规则集。

## Skill 结构

每个 skill 至少有 `SKILL.md`，也可以包含 `agents/openai.yaml`、`scripts/`、`references/` 和 `assets/`。

frontmatter 只要求：

- `name`：不超过 64 个字符，使用小写字母、数字和连字符；
- `description`：不超过 1024 个字符，说明功能和触发条件。

### 命名

名称要容易引用，优先使用描述活动或能力的动名词/动作短语，目录名必须与名称一致。避免含糊的 `helper`、`tools` 和过宽的 `coding`。

### 编写有效 description

description 是主要触发器，不是摘要或完整流程。写清楚“何时使用”和用户可能说出的症状、文件类型、任务名称或同义词。不要把规则、长示例和所有步骤塞进 description。

```yaml
description: 当测试不稳定、包含竞态或依赖时间时使用；用于定位根因并替换任意等待
```

避免“用于异步测试”这类过于抽象的描述，也避免第一人称和无关技术名。正文里的“何时使用”不能代替 frontmatter 触发描述。

## 渐进披露

三层加载结构：

1. 元数据：始终加载，保持极短；
2. `SKILL.md`：触发后加载，只含核心流程，通常少于 500 行；
3. references、脚本和 assets：任务需要时才读取或执行。

### 高层指南 + 参考文件

入口文档说明选择和最短流程：

```markdown
# PDF 处理
## 快速开始
使用 pdfplumber 提取文本；详细表单处理见 `FORMS.md`（任务需要时再读取对应参考文件）。
```

### 按领域组织

金融、销售、产品等互不相关的细节放在一层深度的独立 reference 中，入口只负责导航。不要让一个任务加载全部领域资料。

### 条件式细节

常规编辑放在入口，需要跟踪变更、底层 OOXML 或高级配置时再链接对应 reference。不要在入口重复长篇 API 文档。

### 避免深层引用

引用文件应能从 `SKILL.md` 直接找到。不要让 agent 先读 A 再找 B 再找 C；这会降低可发现性并增加遗漏。

### 为长文件提供目录

超过约 100 行的 reference 在开头提供目录，让 agent 能快速判断是否需要继续读取。每个 reference 只保留一个权威版本，避免内容分叉。

## 工作流和反馈循环

复杂任务使用明确工作流，而不是堆叠原则：

1. 读取输入并确认范围；
2. 建立可验证的中间结果；
3. 执行一个小步骤；
4. 检查结果；
5. 根据反馈调整；
6. 生成最终产物并验证。

### 研究综合流程

先定义问题和来源边界，再收集证据、标记来源、区分事实与推断，最后综合结论并列出不确定性。不要先写结论再寻找支持它的材料。

### 表单填写流程

读取字段规则和已有值，先保存副本；逐字段填写后重新读取校验；对无法确定的字段停止询问，不要猜测；输出前验证格式和必填项。

### 反馈循环

对于生成文档、界面或代码的 skill，先输出可检查的草稿，再让用户或测试反馈驱动下一轮。每次迭代只处理已观察到的问题，避免无限润色。

## 内容审查和文档编辑

### 内容审查

按需求、事实、完整性、结构、语气和格式逐项检查。明确区分阻塞问题和建议。引用文件和行号，避免空泛地说“需要改进”。

### 文档修改

先识别文档格式、结构和保留约束；以局部、可回滚的改动为主；修改后重新读取关键部分并运行格式检查。不要因为修改文字而破坏隐藏元数据、链接、表格或跟踪变更。

### 内容指南

- 不写没有来源的时效性信息；
- 日期、版本和当前状态要带来源或明确标注待确认；
- 对同一概念使用一致术语；
- 事实、推断、建议和未知项分开；
- 示例要短且能验证，不要使用会误导的占位内容。

## 常用输出模式

### 模板模式

模板应提供结构、字段说明和最小示例；可变内容用明确占位符表示，不要让 agent 猜测哪些文字必须替换。

### 报告结构

```markdown
# [分析标题]
## 执行摘要
## 关键发现
## 建议
```

执行摘要只写结论和影响，关键发现带证据，建议带优先级、负责人或下一步。

### 示例模式

示例应覆盖最常见的成功路径和一个关键边界。示例必须与正文规则一致，代码可复制或明确标注为伪代码。

### 提交消息模式

提供仓库实际使用的提交格式和一个真实结构示例。不要假设所有项目都使用同一约定。

### 条件工作流模式

明确分支条件、每条路径的动作、汇合点和失败出口。不要用“视情况处理”替代决策规则。

## 评估与迭代

### 先建立评估

在大量修改 skill 前，准备代表性任务、边界任务和压力任务。定义可观察的成功标准：是否触发、是否读取正确 reference、是否调用正确工具、产物是否合格、是否遵守门禁。

### 迭代开发

从最小规则开始，使用新上下文运行任务，记录原始输出和失败，修改 skill 后重测同类与边界任务。不要把预期答案泄漏给评估代理，也不要只凭“读起来不错”判断效果。

### 观察 agent 如何导航

记录 agent 先读了哪些文件、在哪里停止、哪些 reference 被遗漏、是否重复加载无关资料。根据实际导航调整入口标题、description、链接和文件粒度。

## 避免的反模式

### 避免 Windows 风格路径

跨平台 skill 使用 `/` 和相对路径，必要时说明 Windows 等价写法；不要把某台机器的绝对路径写进通用流程。

### 避免提供过多选项

只提供会影响结果的 2-3 个方案，给出推荐和选择依据。选项过多会增加决策负担并降低执行率。

其他常见反模式：description 过宽、正文只讲理念、文件过长不拆分、没有验证命令、重复资料、用否定规则代替替代动作、加入未被需求支持的功能，以及把历史记录或作者说明混入执行文档。

## 含可执行代码的 Skill

### 解决问题，不要甩锅

如果流程可由脚本可靠完成，就提供脚本并说明输入、输出、退出码和副作用；不要只告诉 agent“自行编写脚本”。脚本不是替代判断的黑箱，失败时要打印足够上下文。

### 实用脚本

脚本应有稳定接口、清晰参数、幂等行为和安全默认值。对删除、覆盖、外部写入和凭据使用明确确认或保护。

```bash
# 典型的重试策略：超时约 30 秒，最多重试 3 次
```

加入 utility script 前确认它确实减少重复工作或提高确定性，并实际运行成功、错误输入和边界测试。

### 视觉分析

需要判断布局、表单结构或图像内容时，可生成可验证的中间截图或结构化分析。不要只说“看起来正常”，指出检查了什么以及证据在哪里。

### 可验证的中间产物

复杂转换分阶段保存输出，例如提取文本、规范化数据、生成草稿、最终打包。每个阶段都能独立检查，失败时容易定位，不要一次生成无法审计的最终结果。

### 依赖和运行环境

列出脚本需要的运行时、包、系统命令和版本约束。不要假设工具已安装；先检测，缺失时报告可执行的安装或降级路径。锁定或读取项目锁文件，避免无意升级。

### MCP 工具引用

在 skill 中引用 MCP 工具时写清服务、工具名、输入 schema、返回值和失败处理。先检测工具是否存在，不能把某个平台专属工具当作通用能力。

## 技术说明

### YAML frontmatter

每个 `SKILL.md` 使用合法 YAML，包含 `name` 和 `description`；名称与目录一致，description 具体且不超过 1024 个字符。不要在 frontmatter 中添加未经支持的字段。

### Token 预算

入口正文通常少于 500 行，频繁加载的 skill 应更短。长细节移入 reference；reference 也要按领域拆分，避免一次加载整套资料。

## 有效 Skill 清单

### 核心质量

- [ ] 触发描述具体、覆盖症状和使用时机；
- [ ] 正文是行动导向而非背景文章；
- [ ] 流程、停止条件和完成标准明确；
- [ ] 规则与项目实际工具和边界一致；
- [ ] 没有无关的 README、历史和重复内容。

### 代码和脚本

- [ ] 脚本参数、退出码和副作用有说明；
- [ ] 失败路径输出足够上下文；
- [ ] 成功、错误、边界和重复执行已测试；
- [ ] 没有假设未安装的工具或平台能力。

### 测试

- [ ] 已用真实任务测试触发和导航；
- [ ] 已测试边界和压力场景；
- [ ] 已验证 agent 读取了正确 reference；
- [ ] 已保存原始失败和修复后的输出；
- [ ] 已运行静态 frontmatter 和引用检查。

## 下一步

先根据具体用户任务写一个最小版本，运行 RED 基线，再补充规则和资源。每次迭代都用证据判断是否改善，最终在部署前使用 `verification-before-completion`。
