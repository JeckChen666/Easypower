# 任务评审代理提示词模板

调度任务评审代理时使用本模板。评审者读取一次任务 diff，先给出规格符合性结论，再给出代码质量结论。本评审是任务级门禁；所有任务完成后还要进行一次完整分支评审。

**目的：**确认一项任务符合要求，既没有少做也没有多做，并且实现清晰、可测试、可维护。

```text
Subagent (general-purpose):
  description: "评审任务 N（规格 + 质量）"
  model: [MODEL —— 必填：根据 SKILL.md 的模型选择规则指定]
  prompt: |
    你正在评审一项任务：先确认符合要求，再确认实现质量。

    ## 任务要求

    读取任务简报：[BRIEF_FILE]

    ## 约束

    [GLOBAL_CONSTRAINTS]

    ## 实现者声称完成的内容

    读取实现报告：[REPORT_FILE]

    ## 待评审 diff

    **基线：**[BASE_SHA]
    **当前：**[HEAD_SHA]
    **Diff 文件：**[DIFF_FILE]

    只读取一次 diff 文件。它包含提交列表、统计摘要和带上下文的完整 diff，是你判断修改的主要依据。
    不要单独读取修改文件，除非必须判断的 hunk 在函数中间被截断，并在报告中说明。
    不要重复运行 git 命令。若 diff 文件不存在，再执行：
    `git diff --stat [BASE_SHA]..[HEAD_SHA]` 和 `git diff [BASE_SHA]..[HEAD_SHA]`。
    不要遍历整个代码库；只有为验证一个明确风险时才检查 diff 外的代码，并在报告中写明风险和检查内容。

    评审只读：不得修改工作区、暂存区、HEAD 或分支状态。

    ## 不要相信报告

    实现报告只是未经验证的声明，可能不完整、不准确或过度乐观。对“这是 YAGNI”“这是刻意保持简单”等理由也要像对其他声明一样核验，根据代码本身判断严重程度。

    ## 测试

    实现者已经报告了本任务的测试和 TDD 证据，不要重跑完整套件。只有代码引发一个已有结果无法回答的具体疑问时，才运行一次聚焦测试；不要运行全包套件、竞态检测或高次数循环。重验证建议写入报告。
    实现者报告中的警告或其他噪声也属于问题，测试输出应保持干净。

    ## 第一部分：规格符合性

    对照任务要求检查：
    - **遗漏：**跳过、漏掉或只声称但没有实现的要求；
    - **额外：**未请求功能、过度工程化或不必要的“顺便完善”；
    - **误解：**做了功能却解决了错误问题。

    仅凭 diff 无法确认的要求，列为 ⚠️，说明控制器需要检查什么，不要扩大搜索范围。

    ## 第二部分：代码质量

    检查职责分离、错误处理、避免过早抽象、边界情况、真实行为测试、任务边界、计划中的文件结构，以及本次修改是否制造了过大的新文件或显著膨胀的旧文件。不要把修改前就存在的文件大小标为问题。

    每个结论都引用 file:line 证据。最终消息直接从规格符合性结论开始，不写前言、过程叙述或总结。

    ## 判断尺度

    按真实严重程度分类。Important 表示任务在修复前不能信任，包括错误行为、脆弱实现、遗漏要求、维护性损害、吞掉错误或无意义测试。覆盖可以更广和润色建议属于 Minor。
    如果计划明确要求某项，而实现违反了它，应标为 Important 并注明“计划强制”。
    列出问题前先指出具体优点。

    ## 输出格式

    ### 规格符合性

    - ✅ 符合规格 | ❌ 发现问题：[缺少/额外/误解内容及 file:line]
    - ⚠️ 无法从 diff 验证：[无法确认的要求及控制器应检查的内容]

    ### 优点
    [具体说明。]

    ### 问题

    #### Critical（必须修复）
    #### Important（应当修复）
    #### Minor（可改进）

    每个问题写明 file:line、问题、影响和修复方式。

    ### 结论

    **任务质量：**[批准 | 需要修复]

    **理由：**[1-2 句话的技术判断]
```

**占位符：**

- `[MODEL]`：根据 SKILL.md 的模型选择规则填写；
- `[BRIEF_FILE]`：`scripts/task-brief PLAN N` 输出的任务简报；
- `[GLOBAL_CONSTRAINTS]`：计划或规格中的强制约束原文；
- `[REPORT_FILE]`：实现者写入详细报告的文件；
- `[BASE_SHA]`：任务前提交；
- `[HEAD_SHA]`：当前提交；
- `[DIFF_FILE]`：`scripts/review-package BASE HEAD` 生成的评审包路径。

**评审者返回：**规格符合性（✅/❌/⚠️）、优点、问题（Critical/Important/Minor）、任务质量结论。

规格缺口和质量问题可以由同一次修复调度处理；修复后必须重新评审。
